# API review rubric

What the operator checks when reviewing a TypeScript API, distilled from two months of design
requests and corrections in Claude and Codex transcripts (2026-07-20 to 2026-09-20; method, counts
and limitations in the [evidence note](#evidence)). [Library API policy](../../../docs/policy/library-api-policy.md)
stays the normative owner: this file says which of its rules get tested first, and adds the review
questions the policy does not state. Each check has an id the guide's scorecard uses.

Score every option against every check: `pass`, `concern`, `fail` or `n/a`, with one sentence of
evidence. A `concern` or `fail` on the recommended option must appear in the guide's open questions.

## How the operator reviews

These shape the guide as much as the checks do.

1. **The public API is the design.** "Everything that happens behind these APIs is an implementation detail that's easy to change later, but we need to get the API design really nailed down... once we have ratified that, we should see a bunch of the eigenquestions fall out" (C 09-05 `6090d1c0`). So the guide comes before the blueprint's implementation detail, and open architectural questions are restated as API choices.
2. **Show it being used.** Requests are for "an API interface sketch", "how a consumer of the runtime would be using those", "how these APIs compose with one another". Call sites lead; type definitions follow.
3. **Findings first, then wait.** The standing instruction is "respond with your findings and recommendations then await; we will discuss before planning further". A guide is delivered for discussion, never silently implemented.
4. **Hypotheses get tested, not defended.** The operator proposes simplifications ("my working hypothesis is that `exportOptions` should always supersede `renderOptions`") and expects them validated or refuted with evidence, then asks which result is "most intuitive".
5. **Adversarial second pass.** After a recommendation: "are all the recommendations sound? any Ponytail simplifications? are all options necessary? any risks with accepting all?" Run that pass before presenting.
6. **Corrections become policy.** When a review finds a rule the policy lacks ("ensure we have this rationale encoded in policy too"), hand it to `create-policy` in the same turn's report.

## Evidence

Method: one streaming pass over 452 Claude and 1,301 Codex transcript files modified since 2026-07-20 kept human-authored user turns matching an API-design vocabulary (1,464 turns after de-duplication; harness injections, tool results, approval requests and delegated lane briefs excluded). The 110 strongest operator turns were read and the checks above paraphrase them. Limitations: a keyword prefilter can miss a correction phrased without any design vocabulary; long turns were read to their first 1,100–1,300 characters; pasted images are unrecoverable; Codex turns that are agent-written lane briefs were treated as the agent's words, not the operator's. This was a targeted review, not an `introspect` run, and it advances no introspection cursor. Session locators are retained in the first guide's run evidence; raw transcript text is not copied into Brain.
