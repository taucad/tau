A changeset or batch write may carry a large-object source, `{ largeObject: oid, size }`, in place of bytes. A provider that declares the `largeObjectSources` capability materialises it from its large-object store; every other provider, and the mutation pipeline in front of one, refuses it with `EINVAL`. `NodeFsProvider` takes a `largeObjectStore` option and lands a source by cloning the stored object (`copyFile` with `COPYFILE_EXCL | COPYFILE_FICLONE`, falling back to a copy), giving it the file's own mode or a new file's default under the umask (never the stored object's, which may be read-only), syncing it and hashing it through its own handle before renaming it into place and syncing the directory: an object that does not hash to its id fails the write with `EINVAL`, the target untouched, and a published entry that is not the hashed file (by device and inode) is `uncertain`. `repositoryLargeObjectStore(repositoryRoot, store)` checks that a store an admission names is the repository's own `.git/lfs/objects`, links resolved. The applied receipt and the Project Index facts carry the source. `serveNodeFsProvider` takes `largeObjectStore(root)` and `NodeFsProviderClient` a `largeObjectSources` option; the Node fs wire protocol is now version 11.
