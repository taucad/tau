# @taucad/api-agent-observability

API agent observability: evidence admission, delivery, erasure and the model-invocation recorder, with telemetry purposes

## Agent observability: the Langfuse plane

This module admits agent evidence, keeps it in an outbox, and delivers each admitted receipt to Langfuse as one OTLP observation. It also reads the ledger values its generations carry back for ledger reconciliation and erases it on request. The rules are in the [agent observability policy](../../../docs/policy/agent-observability-policy.md). This page explains what Langfuse holds and how to read it.

### What Langfuse holds: summary facts, and content where granted

Langfuse is a **summary plane** under policy `purposes-v1`. Every summary observation carries ids, vocabulary values, counts, timings and token usage. It never carries prompts, model output, tool arguments, tool results, file contents or error messages.

- Host facts (`authority: host-reported`) come from the browser host's committed rows (`libs/agent-observability/src/projection.ts`, mapper `host-turn-v5`). The host projects tool, check and outcome facts, the first time a run's text was shown, and ratings (on the feedback plane).
- API facts (`authority: api-reported`) are provider attempts (`model-invocation-evidence.ts`, `api-provider-v3`) and ledger settlements (`settlement-evidence.ts`, `api-settlement-v3`, whose semantic id is the call it settled).
- `coverage.input` and `coverage.output` are `omitted` on every summary fact, or `missing` when content was due but the relay could not capture it. Host facts report `usage: unsupported`, because usage and cost live on the provider and financial facts. An empty Input or Output panel on a summary observation is expected and does not mean data was lost.
- Account, project, run, attempt and record ids reach Langfuse only as keyed or one-way digests (`langfuse.user.id`, `langfuse.session.id`, `metadata.run`, `metadata.chat`, and the trace and object ids). Only the API can link a pseudonym back to an account.
- A provider attempt also carries its input and output (`langfuse.observation.input` and `langfuse.observation.output`) only when two things hold: the deployment's `TAU_OBSERVABILITY_CONTENT_CAPTURE` mode permits the account (`off` by default; `allowlist` admits the ids in `TAU_OBSERVABILITY_CONTENT_ACCOUNTS`; `on`), and the account's `content` purpose is effective for the project. Only the messages new to the call are kept; history, system prompt and tool definitions become digests and counts, images and files become their type and size, and readable thinking is a labelled output part. Text is redacted at capture (`content-v1`) and again at export: any email address and the account's registered email everywhere text is kept, and the account's registered name only in prose (messages, readable thinking, check lines), never in tool arguments, tool results or design source. A tool result over 64 KiB keeps only its size and digest. A withdrawn `content` purpose exports the summary instead.
- Under the same two conditions, a host reports a tool call with its arguments as input and its result as output, and a run's root with this turn's message as input and, as output, the final reply, the source of each model file the run changed (read at the run's final revision; past 128 KiB in total only its size and digest) and one line per check (LW6). The host also falls back to the summary of the same fact when the API refuses, withdraws or cannot hold the content. Every root carries the run's turn measures as metadata: `final_revision`, `files_changed`, `checks_passed`, `checks_failed`, `prior_turns`, `model_calls`, `tool_calls`, `host`, `kernel` and `model` (`start_revision` is not yet reported). The kernel is the one the run targeted, from its turn's snapshot: the chat's chosen kernel, else under `auto` the kernel of the project's main entry; the host sends the same kernel on each model call as `x-tau-kernel`, so the run's generations carry the same `kernel:` tag.

### Why host facts show `protection: unknown`

`metadata.protection` is the **strictest protection across the receipt's lineage**, recorded by the server (`evidence-delivery.ts`). The rank is `free` < `unknown` < `pro`. The host claims only what it knows (`ProjectionContext.protection`), and the API only ever makes that claim stricter. In practice the API-reported facts of a run show `pro` and the host-reported facts of the same run show `unknown`.

This is intentional (charter D12). Do not "fix" it from the AI-training decision. A Langfuse filter on protection should treat `unknown` as at least as strict as the strictest known value.

### How to read a run (`langfuse-v5`)

Each run is **one trace** with **one root**, and each fact is at most one object, written once:

- The trace id is a digest of the environment, principal and run (`execution.attempt`, the id host and API both derive), so every fact of a run lands in the same trace and each turn of a chat is its own trace. `langfuse.session.id` is the chat's keyed group, so a chat's runs share one session.
- The root is an `agent` observation named `run-cad-agent`, with the id `runRootSpanId(environment, principal, run)`. It is written once, from the run's first outcome receipt: it spans from the earliest phase the outcome recorded to the run's end and carries `metadata.termination` and, for a failure, `failure_code`, `failure_owner` and `failure_retry`. Approval waits the host recorded are `wait-for-approval` spans under the root, sent in the same request. A run that never reports an outcome has children and no root.
- A child's id is a digest of its fact's semantic key, so every projection of one fact names one object. Generations are `call-model`, `compact-context` (purpose from the request's activity) or `call-helper-model`; a tool call is named by its first-party tool (`edit_file`, `test_model`) with its evidence class as `tool_class`, and any other tool, including an older host's unnamed fact, as `external-tool` (LW5, LQ5); a settlement is no observation of its own: its values ride on the generation it settled (below). Ratings, checks, presentations, instructions and settlements map to no observation.
- **Scores (LW7).** Ratings and outcomes are Langfuse scores on the run's root observation, written with `POST /api/public/scores` as an array of one: `user-rating` (BOOLEAN, 1 positive, 0 negative) from a rating; `run-termination` (CATEGORICAL: `completed`, `cancelled`, `failed`, `abandoned`) from each outcome receipt, so a resumed run has two, and none for an `unknown` ending; and `task-success` (BOOLEAN) when the host's rule `cad-checks-v1` decided the outcome's `success`: `verified` (1) when the run completed and at least one check at the final revision decided and none failed, `failed` (0) when one of them failed. A check is at the final revision when no `write` or `execute` tool was running or started after it began. A score's id is a digest of its source fact and name and its timestamp is the fact's time, so a repeated write replaces itself. Each names its config by `configId` from `TAU_OBSERVABILITY_SCORE_CONFIG_IDS` (`name=id` pairs, per Langfuse project) when that names one; Tau never reads score configs or scores back.
- A helper or direct model call (`callKind` on the provider fact) is a trace of its own with no parent and no session; when it names a chat, `metadata.chat` carries the chat's group.
- **Generations** start at the relay's start and last as long as the wait plus the stream; `completion_start_time` marks the first relayed byte. Usage is `langfuse.observation.usage_details` with `input` (uncached, normalised per wire in `provider-stream-facts.ts`), `output`, `input_cached_tokens`, `input_cache_creation` and an explicit `total`. Reasoning tokens are part of output and are also `metadata.reasoning_tokens`; on Vertex's completions wire, which reports thinking outside `completion_tokens`, output is their sum, as the ledger counts it. No `cost_details` is sent: Langfuse derives cost from usage, with its per-type breakdown.
- **Ledger values (LW4).** A funded generation carries the ledger's settlement of its call as metadata beside Langfuse's own cost: `supplier_cost_usd` (left out when the ledger could not price it, never zero), `credits` (the customer charge in USD), and `tariff` and `ledger` as keyed digests. Delivery holds a generation whose provider fact names its funded operation (`billing`) and did not fail until that operation's settlement is admitted, for at most `settlementHoldMilliseconds` (60 s) from the generation's admission, and writes the values in the generation's one send; the settlement settles `superseded` with reason `merged`. A generation whose hold runs out goes without them and is counted `unsettled`. A settlement is never sent on its own: one admitted after its generation went settles `superseded` with reason `late` and is written nowhere, because no observation is sent twice; one whose generation is never admitted settles `late` after `settlementOrphanMilliseconds` (15 min). A call with no operation and a failed attempt are not held. The three outcomes are counted on `tau.agent_evidence.settlements` (`merged`, `late`, `unsettled`), and a waiting row on `tau.agent_evidence.deliveries` as `held`.
- **Tags and release.** Every observation carries the trace tag `plan:<protection>` (an array attribute) and `langfuse.trace.metadata.protection`. `langfuse.release` is the first 12 hex digits of the build (the web build's `TAU_RELEASE` on host facts, the API image on API facts), or the label as given; with no build, or the legacy `0000000`, it is `unknown`.
- **Failures.** A failed provider attempt, a failed tool call and a failed run get `level: ERROR` and a status message; an abandoned run and a tool call that ended `unknown` or `cancelled` get `WARNING`. A failed run names its ending code and that code's owner and retry class, for example `run failed: MODEL_ATTEMPT_PENDING (owner host, retry wait)`. An outcome from an older host shows `run failed: unclassified`.
- No phase interval list, `metadata.source` or `metadata.semantic` is sent: the per-phase totals (`wait_ms`, `stream_ms`, `admission_ms`, `approval_ms`) replace the intervals, and the write-side rules below replace read-side deduplication.

To find one run, filter the v2 observations list by `traceId` and sort by `startTime`. Paginate with `cursor`, not `page`.

### Delivery, `superseded` and versions

- Each request carries one receipt's object (a root also carries its approval waits); its scores follow in requests of their own. A partial rejection rejects the receipt, and the receipt is never resent.
- **Exactly once.** Admission settles a source already admitted under another projection version `superseded`: the host is answered with the earlier receipt, as for a replay, and no outbox row is written. A source whose earlier projection was rejected or expired unsent is admitted again. Delivery claims the object's id in the outbox's unique `object_id` before sending; a second receipt for the same object settles `superseded` with reason `object`, and a fact that maps to no object settles `superseded` with reason `no-object`. A settlement settles `superseded` with reason `merged` or `late` (LW4). Each is counted on `tau.agent_evidence.superseded_receipts` by reason (`reprojected`, `object`, `no_object`, `merged`, `late`). Reconciliation looks the object up by its stored id.
- **Langfuse units.** Hobby allows 50k units a month, a unit being a trace, an observation or a score (Langfuse blueprint LW24, ruling 13). Delivery counts them on `tau.agent_evidence.langfuse_units` by `kind`, once per object: at an accepted answer, an observation for each span and a trace as well for each span with no parent, and a score for each score write Langfuse accepted; for a send whose answer was uncertain, one observation when reconciliation finds its object. A superseded receipt, a refused send and a gap add nothing. `agent-evidence-langfuse-units` fires at 35,000 units in 31 days (70%).
- **Cutover from `langfuse-v4.3`.** A fact first delivered under v4.3 already has its receipt, so a later re-projection is `superseded` and nothing is sent again in the new shape. Receipts still pending at the deploy are mapped under v5; a send still being reconciled across it, with no stored object id, is looked up by its old receipt-derived span id. A run in flight across the deploy is split between an old chat trace and a new run trace, told apart by `metadata.mapper`. Old `tau.*` rows leave with retention. A settlement admitted as `api-settlement-v2` before the LW4 deploy names its ledger entry, not its call, so no generation takes it: it settles `late` after its bound, and reconciliation reads it as missing.
- **Readers.** Runs, attempts and phases are read from the Langfuse dashboards (LQ10). The Tau readers (`langfuse-client.ts` `observations`, `langfuse-scorecard.ts`, `ledger-reconciliation.ts`) read only generations (`call-model`, `compact-context`, `call-helper-model`) written by v5 and reported by the API, take the charge and the ledger id from their metadata, count a settlement once by its ledger id, and read no interval list. They no longer read `tau.financial` spans, so a settlement written as one before LW4 reads as missing coverage, never as drift; so does a `late` settlement.
- **Score writes.** An outcome's scores are written after its root's one send has an answer that is not `not-sent` (also when its root was already claimed by an earlier outcome), so a retried send never writes them twice; a rating writes only its score and settles by its answer: `confirmed` on 202, `rejected` on a 207 (never retried), retried when the write never reached Langfuse, and `expired` with reason `score-uncertain` when it stayed uncertain after three identical sends. A score whose config id is not set is written without `configId`, under the same id, so roots and scores never wait for the configs. Each write is counted on `tau.agent_evidence.scores` by score and outcome (`accepted`, `rejected`, `uncertain`, `not_sent`), with `tau.agent_evidence.score_configured` `false` for a score written without a config id.
- A host outcome fact with `failureClass` and `code` is refused (`EVIDENCE_INVALID`) by an API built before those fields existed. The host drops a refused envelope and counts it (`libs/agent-observability/src/delivery.ts`), so the only cost is lost evidence. Agent work never waits on delivery.

### Erasure

Deleting an account erases what Tau sent to Langfuse (`evidence-erasure.ts`, `evidence-erasure.service.ts`). Admission of the erasure stops every unsent row and copies every trace id a send may have written into a journal that outlives the account. Fifteen minutes later, once a span accepted just before the fence has been ingested, the lifecycle pass sends `DELETE /api/public/traces` for those traces. An accepted delete is the erasure (charter I6 as amended by ruling 9): the trace settles `accepted`, and the erasure completes once every trace it named is accepted. Tau never reads Langfuse to confirm a delete; a periodic drill proves that an accepted delete removes a trace and its scores. A refused delete is retried with backoff and counted as `retry`, and `agent-evidence-erasure-stuck` fires when deletes have been retried for 2 h with none accepted. Journal rows settled `absent` were read back before the amendment and keep that value.
