# @taucad/files-ui

The files feature of the Tau UI app: file and workspace-directory components, the file tree, export-format derivation, workspace telemetry, the file-manager helpers that read no app state and the project library's core (its three machines, entry and journal types, project URLs and names, and its storage calls and filesystem observations behind injected seams). Private and source-consumed (`scope:ui type:app-lib layer:feature`): `apps/ui` imports it; it imports only app-libs and packages, never `apps/ui`.

Cut from `apps/ui/app/{components/files,components/filesystem,filesystem,machines,runtime,types,utils}` in UI wave D (CI decomposition blueprint, Part 3 P2 row D). It grows as the modules it waits on leave the app.

## File services

`use-file-content` and `use-file-tree` read `{ contentService, treeService }` from `FileServicesProvider`, never from the app's file manager. `apps/ui`'s `FileManagerProvider` renders the provider inside its own context. `useFileContent` and `useFreshContent` throw outside a provider; `useFileTreeSelector` degrades to an empty tree, so presentation-only surfaces render outside a project. An app suite that mocks `#hooks/use-file-manager.js` and renders a component reading these hooks also mocks `@taucad/files-ui/hooks/use-file-services`, delegating `useFileServices` and `useOptionalFileServices` to the mocked `useFileManager` so both read the same services.

## Project library

The three library machines are the formal core of `ProjectLibrary`: `apps/ui/specs/library-catalog` checks them against `LibraryCatalog.tla` and hashes them here, so a change to one goes through that spec first (`FORMAL_UPDATE=1`). `runtime/project-library-storage` and `runtime/project-library-observations` are the calls and watches the machines run as ports. They take the facade, the object-store worker and the chat store as arguments typed by `types/project-library-io.types` (`ProjectLibraryFileManager`, `ProjectLibraryObjectStore`, `ProjectLibraryChatRecords`): only the members they read, so the app passes its `ProjectLibraryFacade`, `Remote<ObjectStoreWorker>` and chat store unchanged. The storage root key reads the database prefix from `@taucad/ui-core/constants/meta.constants`, the value the app hands its file-manager worker. `machines/workspace-connection.machine` reports its first fault through the `reportFault` member of its injected services, and `runtime/project-library-workspace` reads the facade's `workspace` and the worker's journal (`WorkspaceJournal`) structurally, so `ProjectLibrary` passes its runtime fault reporter, facade and `Remote<ObjectStoreWorker>` in. The app's `ProjectLibrary` service and commands, `hooks/project-manager.machine.ts`, `use-project-manager` and `use-projects` run them; those stay in the app (see below).

## Build target

Desktop-only branches read `isDesktopTarget` from `@taucad/ui-core/lib/build-target`, a literal the desktop build resolves to its `tau-desktop` variant, so those branches fold out of the web bundle. Tests choose a variant with `vi.mock('@taucad/ui-core/lib/build-target', …)`, not `vi.stubEnv`.

## Still in the app

`use-file-manager`, `use-native-file-manager`, `chat-editor-file-tree`, the file-manager machine and worker, `filesystem/{build-skew,desktop-quick-look,file-operation-participants}` and the remaining `components/files` and `components/filesystem` modules. Their closures reach `#environment.config`, `#runtime/*`, `lib/agent-host-placement`, `use-project`, `use-project-manager` or the CAD machine; `build-skew` belongs to the build lifecycle. `use-file-manager` reaches about 850 app modules through `#runtime/*`, and every remaining `components/files` and `components/filesystem` module reaches it.

The rest of the project-library runtime stays. The app's facade type `ProjectLibraryFacade` stays in `runtime/file-manager-facade.ts` (it is `Pick<ReturnType<typeof useFileManager>, …>`). `project-library.ts` and `project-library-commands.ts` add the chat-session store, kernel utils (`?raw` lockfiles), `tau-cloud-intent` and the project-manager machine, which starts the app's object-store worker and reports through `app-runtime-faults`. `use-project-manager` and `use-projects` sit on the app runtime provider. `types/storage.types.ts` now has a clean closure but is the app's chat and preference storage contract, not the library's. `utils/project-url.utils.node.test.ts` stays because it scans `apps/ui/app` sources.
