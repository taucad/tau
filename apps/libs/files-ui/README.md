# @taucad/files-ui

The files feature of the Tau UI app: file and workspace-directory components, the file tree, export-format derivation, workspace telemetry, the file-manager helpers that read no app state, the Quick Look action, and the project library's core (its three machines, entry and journal types, project URLs and names, its storage calls and filesystem observations, its service and commands, and the project manager's provider and listing hook, behind injected seams). Private and source-consumed (`scope:ui type:app-lib layer:feature`): `apps/ui` imports it; it imports only app-libs and packages, never `apps/ui`.

Cut from `apps/ui/app/{components/files,components/filesystem,filesystem,hooks,lib,machines,runtime,types,utils}`. It grows as the modules it waits on leave the app.

## File services

`use-file-content` and `use-file-tree` read `{ contentService, treeService }` from `FileServicesProvider`, never from the app's file manager. `apps/ui`'s `FileManagerProvider` renders the provider inside its own context. `useFileContent` and `useFreshContent` throw outside a provider; `useFileTreeSelector` degrades to an empty tree, so presentation-only surfaces render outside a project. An app suite that mocks `#hooks/use-file-manager.js` and renders a component reading these hooks also mocks `@taucad/files-ui/hooks/use-file-services`, delegating `useFileServices` and `useOptionalFileServices` to the mocked `useFileManager` so both read the same services.

## Project and file manager

`file-link`, `viewer-link` and `open-render-button` read the open project from `ProjectContext` (`@taucad/ui-core/contexts/project-context`). It types only what they use: `projectId`, `projectRef.send` with `openInViewer`, and `editorRef.send` with `openFile` and `revealFileInTree`. The app's project providers put the whole project in it, and the app's `useProject` reads it back as the app's type. Outside a project the links do nothing. `file-selector` reads the tree service from `FileServicesProvider`. Their suites render inside `ProjectContext.Provider` or mock `#hooks/use-file-services.js`; an app suite that mocks `#hooks/use-project.js` does not reach them.

## Project library

The three library machines are the formal core of `ProjectLibrary`: `apps/ui/specs/library-catalog` checks them against `LibraryCatalog.tla` and hashes them here, so a change to one goes through that spec first (`FORMAL_UPDATE=1`). `runtime/project-library-storage` and `runtime/project-library-observations` are the calls and watches the machines run as ports. They take the facade, the object-store worker and the chat store as arguments typed by `types/project-library-io.types` (`ProjectLibraryFileManager`, `ProjectLibraryObjectStore`, `ProjectLibraryChatRecords`): only the members they read, so the app passes its `ProjectLibraryFacade`, `Remote<ObjectStoreWorker>` and chat store unchanged. The storage root key reads the database prefix from `@taucad/ui-core/constants/meta.constants`, the value the app hands its file-manager worker. `machines/workspace-connection.machine` reports its first fault through the `reportFault` member of its injected services, and `runtime/project-library-workspace` reads the facade's `workspace` and the worker's journal (`WorkspaceJournal`) structurally, so `ProjectLibrary` passes its runtime fault reporter, facade and `Remote<ObjectStoreWorker>` in. `machines/project-manager.machine` holds the object-store worker: its input (`ProjectManagerServices`) carries `startObjectStore`, which returns the worker and its store as `ProjectLibraryObjectStore`, plus `reportFault` and `reportWorkerFailed`. `ProjectLibrary` passes its worker factory, `reportAppRuntimeFault` and `reportProjectLibraryWorkerFailed`, and reads the store back as its worker.

`runtime/project-library` (`ProjectLibrary`) and `runtime/project-library-commands` (`ProjectCommands`) run them. Both are generic over the worker (`ProjectLibraryWorker`), the root facade (`ProjectLibraryRootFacade`) and the chat projection, and take what only the app supplies as `ProjectLibraryServices`: `startObjectStore`, `reportFault`, `reportWorkerFailed`, `buildSkew` (the write stop a newer build sets), `createChatStore`, `clearLegacyListing`, and the commands' `ProjectCommandsServices`: `projectTemplates` (the project constants and the kernel helpers, which read the kernel plugins' lock files), `buildUserMessage`, `cloudIntent` (Tau Cloud's backup intent) and `isCaughtUp` (a chat projection's catch-up). `apps/ui/app/runtime/project-library.ts` is the app's binding: a `ProjectLibrary` subclass that fixes the three types and passes services that read their app modules when called, so a suite that mocks one of those modules still reaches the library through it. The create-project lock is `withNamedLock` from `@taucad/ui-core/lib/named-lock`, shared with the app's Tau Cloud gestures.

`hooks/project-manager-provider` composes a `ProjectLibrary` into the value `useProjectManager` (`hooks/use-project-manager`) reads. Its worker is a `ProjectManagerWorker` (the library's worker plus the GeoSpec consent and the chrome preferences), and it takes what only the app supplies as `ProjectManagerServices`: `generateProjectName`, `seedChatPermission`, `removeChatPermission` and `prepareFirstProjectTour`. The context lives in `use-project-manager`, apart from its provider, so an edit to the provider keeps it. `hooks/use-projects` takes the project manager, the chat session store and the view exceptions as inputs (`ProjectsInputs`). The app keeps bindings at `hooks/use-project-manager.tsx` and `hooks/use-projects.ts`: the first resolves the runtime's library and passes its services, and re-exports `useProjectManager`; the second passes the app's `useProjectManager()` result, so suites that mock either app path still reach every reader.

## Build target

Desktop-only branches read `isDesktopTarget` from `@taucad/ui-core/lib/build-target`, a literal the desktop build resolves to its `tau-desktop` variant, so those branches fold out of the web bundle. Tests choose a variant with `vi.mock('@taucad/ui-core/lib/build-target', …)`, not `vi.stubEnv`.

## Still in the app

`use-file-manager`, `use-native-file-manager`, `chat-editor-file-tree`, the file-manager machine and worker, `filesystem/build-skew` and the remaining `components/files` and `components/filesystem` modules. Their closures reach `#environment.config`, `#runtime/*`, `lib/agent-host-placement`, `use-project` or `use-project-manager`. `use-file-manager` reaches about 850 app modules through `#runtime/*`; `workspace-connections` reads it, `workspace-selector` reaches it through `use-project-creation-location`, and `directory-link` reads `use-project` and the project route's workspace context. `unavailable-folders-notice` reads only the file manager's ref, which the shared `FileManagerContext` could carry, but it loads in Home's critical tier, so it stays with Home's budget.

`filesystem/build-skew` (`#lib/build-identity`, which reads `window.ENV` and build globals) and `use-native-file-manager` (`lib/agent-host-placement`) could take their app values through injected seams, but both load in Home's critical tier, and the bindings and wrappers a seam needs there add more brotli bytes than Home's critical budget leaves. `routes/w.$workspace.$project/chat-editor-file-tree.tsx` passes Quick Look its desktop kernel (`#constants/desktop-kernel-options`) and loads `#telemetry/runtime-telemetry` only for a conversion.

The project library's app binding stays at `runtime/project-library.ts`, with what it binds: the object-store worker (`hooks/object-store-worker`, started by `new URL(…, import.meta.url)`), the reporters (`app-runtime-faults`, `file-service-reports`, both through `#lib/error-reporting`), `filesystem/build-skew` (`#lib/build-identity`, which reads `window.ENV` and build globals), `db/chat-file-storage` (the app's chat store), `constants/project.constants` (named by path by `scripts/src/check-standalone-project.ts` and the native Darwin lane paths in `ci.yml`), `utils/kernel.utils` (`?raw` lock files), `utils/chat.utils` (the app version in `metaConfig.userAgent`, and types from `#hooks/use-models`), `lib/tau-cloud-intent` (the revision session user) and `machines/chat-projection.logic` (the chat SDK loader). So do its test rows that need the app runtime or device storage, and `runtime/project-library.fixture.ts`, which types files-ui's fixture by the app's facade. The app's facade type `ProjectLibraryFacade` stays in `runtime/file-manager-facade.ts` (it is `Pick<ReturnType<typeof useFileManager>, …>`). The `use-project-manager` suites stay in the app: they compose the app's `ProjectLibrary` binding and runtime and mock its modules. `types/storage.types.ts` keeps the app's object-store contract; only `ChatStorage` and `AppUiPreferences` moved. `utils/project-url.utils.node.test.ts` stays because it scans `apps/ui/app` sources.
