# Embedding in a Host

The `transport` option on `createRuntimeClient` is the single seam where the host supplies an opaque filesystem to the runtime. Transport-owned signalling and geometry memory are closed over at construction. `client.connect()` takes no arguments in v6; it only runs the handshake for the transport that was supplied at construction.

This guide covers the three scenarios where explicit transport wiring is the right choice:

1. **Worker-hosted filesystems** -- trusted host code selects a project route and exposes a fresh rooted bridge connection via `fromFileSystemBridge(() => connection)`.
2. **Deferred client creation** -- the runtime client is constructed once the host knows which filesystem to bind to.
3. **Electron utility-process hosts** -- the runtime executes outside the renderer behind the bundled main, preload, utility, and renderer helpers.

If none of these apply, head back to the [Quick Start](../getting-started/quick-start) or [Live Rendering](./live-rendering) guides -- they are the canonical npm-consumer paths.

## Why a Host Would Wire This Manually

A host (CAD editor, IDE, multi-user platform) typically owns the filesystem and worker explicitly:

- A single filesystem authority serving multiple independently rooted runtime clients
- Externally managed lifecycle (the host already owns "the project filesystem"; the runtime is just a consumer)
- The ability to terminate and re-create runtime clients without losing the underlying filesystem

`createWebWorkerClientOptions({ fileSystem, ... })` is the common browser seam where the host hands that opaque filesystem to the runtime. Transport authors can use `webWorkerTransport({ fileSystem, ... })` directly.

## Opaque `RuntimeFileSystem` values

The **`fileSystem`** field on `webWorkerTransport({ ... })`, `inProcessTransport({ ... })`, and friends accepts an opaque [`RuntimeFileSystem`](../api/filesystem) value. The value is produced by one of the bundled factory functions — consumers cannot inspect its internals. The transport constructs the underlying bridge primitives from it:

| Factory                              | When to use                                    |
| ------------------------------------ | ---------------------------------------------- |
| `fromMemoryFs({ 'main.ts': '...' })` | Static fixtures, tests, CLI one-shots          |
| `fromFsLike(myFs)`                   | Wrap a custom `RuntimeFileSystemBase` impl     |
| `fromNodeFs('/srv/projects/widget')` | Headless / Node.js (CLI, benchmarks, server)   |
| `fromBrowserFs(directoryHandle)`     | Browser File System Access API root            |
| `fromFileSystemBridge(open)`         | Editor host with a fresh rooted bridge factory |

### Worker-hosted filesystems

When the host owns a File Manager Worker (the canonical editor pattern), trusted composition selects an authority-global project route. Pass a connection factory to `fromFileSystemBridge(...)`; every runtime binding or initialize retry receives a fresh bridge rooted at that project:

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { createWebWorkerClientOptions } from '@taucad/runtime/transport/web';
import { fromFileSystemBridge, openFileSystemBridge } from '@taucad/runtime/filesystem';

const fileManagerWorker = new Worker(new URL('./fm-worker.ts', import.meta.url));

const clientOptions = createWebWorkerClientOptions({
  createWorker: () => new Worker(new URL('./runtime.worker.ts', import.meta.url), { type: 'module' }),
  fileSystem: fromFileSystemBridge(() => openFileSystemBridge(fileManagerWorker, { root: '/projects/widget' })),
});
const client = createRuntimeClient(clientOptions);
await client.connect();

const result = await client.export('glb', { source: { path: 'main.ts' } });
if (!result.success) throw new Error(`Export failed: ${result.issues[0]?.message}`);

client.terminate();
```

The runtime worker entry owns `defineRuntime(...)`; the client imports only the runtime type when it needs compile-time narrowing.

The transport owns and disposes each connection returned by the factory. Runtime does not know whether the filesystem authority is a Worker, iframe, Electron utility process, or another port broker. It also receives no project id, authority-global path, rights object, or mount table; it simply renders local paths exposed by the filesystem.

In the example, the host-owned authority path `/projects/widget/main.ts` becomes runtime `main.ts`. Kernels and bundlers receive only the latter. See [Path Namespaces](../concepts/path-namespaces) for the equivalent Node, browser-handle, memory, and inline-source mappings.

### In-process filesystems

For tests, CLIs, and other same-thread scenarios, use `inProcessTransport` with an inline filesystem:

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { fromMemoryFs } from '@taucad/runtime/filesystem';
import { defineRuntime } from '@taucad/runtime/worker';
import { replicad } from '@taucad/replicad';
import { inProcessTransport } from '@taucad/runtime/transport/in-process';

const runtime = defineRuntime({ plugins: [replicad()] });
const client = createRuntimeClient({
  transport: inProcessTransport({
    runtime,
    fileSystem: fromMemoryFs({
      'main.ts':
        "import { drawCircle } from 'replicad';\nexport default () => drawCircle(10).sketchOnPlane('XY').extrude(20);",
    }),
  }),
});
await client.connect();
```

The transport detects the inline arm and wires an in-process bridge that auto-propagates `watch` events when the wrapped FS exposes a `watch` method — so editor edits flow through the same dependency-invalidation pipeline as worker-hosted FSes.

## Why the runtime has no host file-pool option

Do not pass the filesystem authority's shared file pool to a rooted runtime. A pool hit can return authority-global bytes before the scoped bridge handles the read, bypassing the filesystem boundary. Runtime file content therefore uses the rooted bridge's transfer/copy path. Transport-owned geometry and cooperative-abort memory remain internal; a capability-local filesystem pool can be introduced later only if measurement justifies it.

## Electron utility-process hosts

Electron uses one utility process per materialized runtime client. The bundled main, preload, utility, and renderer helpers exchange an opaque host lease internally so normal close and hard timeout recovery terminate exactly that process.

Register the utility entry in the main process:

```typescript @ts-nocheck
// main.ts
// @ts-nocheck: the docs resolver cannot resolve electron-vite's `?modulePath` virtual specifier.
import { app } from 'electron';
import { installElectronRuntimeHeaders, registerElectronRuntimeMain } from '@taucad/runtime/electron/main';
import utilityEntry from './runtime.utility?modulePath';

await app.whenReady();
installElectronRuntimeHeaders();
const runtimeMain = registerElectronRuntimeMain({
  utilityEntry,
});

app.once('before-quit', () => runtimeMain.dispose());
```

Expose the narrow bridge from preload:

```typescript
// preload.ts
import { exposeElectronRuntime } from '@taucad/runtime/electron/preload';

exposeElectronRuntime();
```

Serve the worker-owned runtime in the utility process:

```typescript
// runtime.utility.ts
import { fromMemoryFs } from '@taucad/runtime/filesystem';
import { serveElectronRuntime } from '@taucad/runtime/electron/utility';
import { runtime } from './examples/runtime-definition';

serveElectronRuntime({
  runtime,
  fileSystem: fromMemoryFs(),
});
```

Create the renderer client through the async options provider:

```typescript
// renderer/runtime-client.ts
import { createRuntimeClient } from '@taucad/runtime/client';
import { createElectronClientOptions } from '@taucad/runtime/electron/renderer';

const provideClientOptions = createElectronClientOptions({ renderTimeout: 60_000 });

export const createElectronRuntimeClient = async () => createRuntimeClient(await provideClientOptions());
```

Renderer code should never handle the host ID or call `releaseRuntimeHost` itself. The transport releases its lease through the preload bridge when `RuntimeClient.terminate()` runs or when a render timeout requires hard recovery. The config and `?modulePath` import are identical on electron-vite 5/Vite 7 and electron-vite 6 beta/Vite 8. See [Bundling](./bundling) for electron-vite configuration and [Configure Render Timeouts](./render-timeouts) for the typed restart flow.

## Deferred Client Creation

When the host needs a runtime client before it knows which filesystem to bind to (e.g. the client is created at app boot and the project is chosen on user navigation), construct the client once the filesystem is known:

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { defineRuntime } from '@taucad/runtime/worker';
import { replicad } from '@taucad/replicad';
import { inProcessTransport } from '@taucad/runtime/transport/in-process';
import { fromNodeFs } from '@taucad/runtime/filesystem/node';

// ...later, once the user picks a project:
const projectPath = '/Users/me/cad-projects/widget';
const runtime = defineRuntime({ plugins: [replicad()] });
const client = createRuntimeClient({
  transport: inProcessTransport({ runtime, fileSystem: fromNodeFs(projectPath) }),
});
await client.connect();
```

Because every wire concern is closed over at construction time, the client stays in the `'unconnected'` lifecycle state until `connect()` is called — no worker is spawned, no transport handshake runs. This is the correct pattern for editors that want to instantiate clients lazily once the workspace is known.

## Lifecycle and Re-connection

`client.connect()` is **idempotent**: calling it a second time while already connected resolves immediately without re-running the handshake. To switch a client to a different project, terminate the existing client and create a fresh one with the new transport options.

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { fromMemoryFs } from '@taucad/runtime/filesystem';
import { defineRuntime } from '@taucad/runtime/worker';
import { replicad } from '@taucad/replicad';
import { inProcessTransport } from '@taucad/runtime/transport/in-process';

const runtime = defineRuntime({ plugins: [replicad()] });
const client = createRuntimeClient({
  transport: inProcessTransport({
    runtime,
    fileSystem: fromMemoryFs({ 'main.ts': 'export default () => 1;' }),
  }),
});

// Idempotent: calling connect() again resolves immediately.
await client.connect();
await client.connect();

// To switch projects: terminate and create a new client.
client.terminate();
```

The lifecycle progression is `'unconnected' -> 'connecting' -> 'connected' -> 'terminated'`. Inspect the current state via `client.lifecycleState` -- helpful for host-level diagnostics and React state derivation.

### Deterministic `terminate()` and graceful `shutdown()`

`client.terminate()` is **synchronous** and observes seven invariants the host can rely on without timing-dependent shutdown choreography:

1. `client.lifecycleState` becomes `'terminated'` synchronously.
2. The transport's `close()` is invoked exactly once.
3. Every in-flight `connect()` / `render()` / `updateParameters()` / `setOptions()` / `export()` Promise rejects on the next microtask with `RuntimeTerminatedError` (`causeKind: 'explicit'`).
4. `client.on(...)` calls made after `terminate()` throw synchronously (subscription is no longer meaningful).
5. Subsequent commands reject synchronously with `RuntimeTerminatedError` (`causeKind: 'explicit'`).
6. A second `terminate()` call is a no-op (idempotent).
7. Captured connect options are cleared so a fresh client created from the same host primitives starts from a clean slate.

For orderly shutdown paths (`beforeunload`, server graceful-exit, integration test teardown) the asynchronous `shutdown({ drain? })` companion lets the host await in-flight intents before tearing down:

```typescript
function attachShutdown(client: { shutdown: (opts: { drain?: boolean }) => Promise<void> }): void {
  window.addEventListener('beforeunload', () => {
    void client.shutdown({ drain: true });
  });
}
```

`shutdown({ drain: true }){:ts}` closes command admission, waits for already-admitted intents, awaits the worker's one idempotent cleanup call behind its serialized operation lane, and only then closes the transport and owned bridge resources. `terminate(){:ts}` and `shutdown({ drain: false }){:ts}` are hard closes: they reject promptly and make no claim that remote kernel/filesystem cleanup ran. A concurrent hard terminate unblocks a drain. All paths are idempotent.

Wire this from your host after you construct the client — for example `attachShutdown(client){:ts}` where `client` is your `RuntimeClient{:ts}`.
