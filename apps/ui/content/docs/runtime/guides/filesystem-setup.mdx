# Set Up the Filesystem

Configure the filesystem backend that kernels use to read project files. The framework provides adapters for Node directories, browser directory handles, in-memory content, already-confined fs-compatible objects, and host-owned filesystem bridges.

## Prerequisites

- [Install @taucad/runtime](../getting-started/installation)
- Completed the [Quick Start](../getting-started/quick-start)

## Goal

Choose and configure a filesystem implementation so your runtime client can read (and optionally write) project files during render, export, and parameter extraction.

## Steps

### 1. Import Filesystem Constructors

`fromMemoryFs`, `fromFsLike`, and `fromFileSystemBridge` are available from the filesystem entry. Environment-specific adapters use their Node.js and browser subpaths:

```typescript
import { fromMemoryFs, fromFsLike, fromFileSystemBridge } from '@taucad/runtime/filesystem';
import { fromNodeFs } from '@taucad/runtime/filesystem/node';
import { fromBrowserFs } from '@taucad/runtime/filesystem/browser';
```

### 2. Use fromNodeFs for Disk-Based Projects

Use `fromNodeFs` when your project files live on disk. Pass the base path; all file operations are resolved relative to it. Requires Node.js (not available in browser projects).

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { fromNodeFs } from '@taucad/runtime/filesystem/node';
import { inProcessTransport } from '@taucad/runtime/transport/in-process';
import { defineRuntime } from '@taucad/runtime/worker';
import { replicad } from '@taucad/runtime/kernels';
import { esbuild } from '@taucad/runtime/bundler';

const runtime = defineRuntime({
  kernels: [replicad()],
  bundlers: [esbuild()],
});

const client = createRuntimeClient({
  transport: inProcessTransport({ runtime, fileSystem: fromNodeFs('/path/to/project') }),
});
```

Use this when running in Node.js (CLI, tests, server-side) and when you need persistent cache (e.g., geometry cache, parameter cache).

### 3. Use fromMemoryFs for In-Memory Content

Use `fromMemoryFs` when file content is passed directly (e.g., from an editor) or when you want no disk I/O. Optionally seed with initial files:

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { fromMemoryFs } from '@taucad/runtime/filesystem';
import { inProcessTransport } from '@taucad/runtime/transport/in-process';
import { defineRuntime } from '@taucad/runtime/worker';
import { replicad } from '@taucad/runtime/kernels';
import { esbuild } from '@taucad/runtime/bundler';

const filesystem = fromMemoryFs({
  'main.ts': `
    import { drawRoundedRectangle } from 'replicad';
    export default function main() {
      return drawRoundedRectangle(30, 50, 5).sketchOnPlane('XY').extrude(10);
    }
  `,
  'lib/utils.ts': 'export function helper() { return 42; }',
});

const runtime = defineRuntime({
  kernels: [replicad()],
  bundlers: [esbuild()],
});

const client = createRuntimeClient({
  transport: inProcessTransport({ runtime, fileSystem: filesystem }),
});
```

### 4. Use fromFsLike for an Already-Confined fs-Compatible Object

Use `fromFsLike` when an fs-compatible object with a `promises` namespace already exposes exactly the virtual tree the runtime may access (for example BrowserFS or memfs). It adapts that existing namespace and does not select or enforce a root. The `FsLike` interface requires `promises.readFile`, `promises.writeFile`, `promises.mkdir`, and the other standard `fs.promises` methods:

```typescript
import { createRuntimeClient } from '@taucad/runtime';
import { fromFsLike } from '@taucad/runtime/filesystem';
import { inProcessTransport } from '@taucad/runtime/transport/in-process';
import { defineRuntime } from '@taucad/runtime/worker';
import { replicad } from '@taucad/runtime/kernels';
import { esbuild } from '@taucad/runtime/bundler';

const filesystem = fromFsLike(alreadyConfinedVirtualFs);

const runtime = defineRuntime({
  kernels: [replicad()],
  bundlers: [esbuild()],
});

const client = createRuntimeClient({
  transport: inProcessTransport({ runtime, fileSystem: filesystem }),
});
```

For a raw Node filesystem, use `fromNodeFs('/path/to/project')`; that adapter maps the selected host directory to virtual `/` and enforces lexical and symlink containment at the adapter boundary.

### 5. Use fromBrowserFs for a Browser Directory

Use `fromBrowserFs` when the user grants a `FileSystemDirectoryHandle`. The selected handle becomes runtime `/`; runtime `/main.ts` refers to `main.ts` beneath that handle and never to the host operating system's root:

```typescript
import { fromBrowserFs } from '@taucad/runtime/filesystem/browser';

const directory = await window.showDirectoryPicker();
const filesystem = fromBrowserFs(directory);
```

### 6. Understand RuntimeFileSystemBase, KernelFileSystem, and RuntimeFileSystem (opaque)

The framework uses three related filesystem types:

**`RuntimeFileSystem`** -- The opaque connect-time value returned by `fromNodeFs`, `fromMemoryFs`, `fromFsLike`, `fromBrowserFs`, and `fromFileSystemBridge`. Hand it to the wired transport callable at construction (`webWorkerTransport({ fileSystem })`, `inProcessTransport({ runtime, fileSystem })`, …); consumers cannot inspect its internals.

**`RuntimeFileSystemBase`** -- The 11-method contract bridged to the kernel. Matches `fs.promises` semantics: `readFile`, `writeFile`, `mkdir`, `readdir`, `unlink`, `rmdir`, `rename`, `stat`, `lstat`, `exists`.

**`KernelFileSystem`** (framework view) -- An enhanced interface that extends the base with convenience methods inside the worker. The framework wraps the base automatically via `createRuntimeFileSystem(base)`:

| Method            | Signature                                          | Default Implementation                       |
| ----------------- | -------------------------------------------------- | -------------------------------------------- |
| `readFiles`       | `(paths) => Promise<Record<string, Uint8Array>>`   | `Promise.all(paths.map(readFile))`           |
| `readdirContents` | `(dirPath) => Promise<Record<string, Uint8Array>>` | `readdir` + `stat` + `readFile` (files only) |
| `readdirStat`     | `(dirPath) => Promise<FileStatEntry[]>`            | `readdir` + `stat` per entry                 |
| `ensureDir`       | `(path) => Promise<void>`                          | `mkdir(path, { recursive: true })`           |

Every method accepts a [runtime path](../concepts/path-namespaces) within the supplied filesystem. For a project-rooted filesystem, `/main.ts`, `/.tau/cache`, and `/node_modules` are local to that project; the leading slash is not the host OS root. Backends can supply optimized overrides for any enhanced method.

`fromNodeFs` is watch-capable: it opens one non-recursive `fs.watch` on the parent directory of each path in the kernel's dependency set, filters events by filename against that set, and classifies each hit by `stat`. A Node- or Electron-hosted runtime therefore rerenders autonomously when something outside the runtime edits a dependency.

Watcherless adapters (`fromMemoryFs`, `fromBrowserFs`, and arbitrary `fromFsLike`) do not fabricate subscriptions. Each explicit source-bearing render/export operation rereads its current filesystem snapshot while keeping kernel initialization and persistent `/.tau/cache` entries reusable. Autonomous rerendering requires a real watch-capable filesystem.

### 7. Use Filesystem Bridges for Cross-Worker Communication

When the filesystem owns a **`Worker`** (**`exposeFileSystem`** there) and the client runs in another isolate, pass a factory to **`fromFileSystemBridge(openConnection)`** from **`@taucad/runtime/filesystem`**. For a persisted project, the factory calls **`openFileSystemBridge(worker, { root: '/projects/<id>' })`** from the same public runtime subpath so every runtime binding or retry gets a fresh rooted connection. Use **`createFileSystemBridge(worker)`** plus **`createFileSystemBridgeProxy<T>(bridge)`** when the current isolate needs to call filesystem methods directly.

**`openFileSystemBridge(worker, options?)`** -- Creates a **`MessageChannel`**, posts the server end to the FS worker, and returns a raw transferable filesystem bridge connection for another consumer such as runtime.

**`createFileSystemBridge(worker, options?)`** -- Creates a **`MessageChannel`**, posts the server end to the FS worker, returns **`FileSystemBridge`** with a **`wrapMessagePort`**-backed **`port`** for same-isolate **`createFileSystemBridgeProxy`**.

**`exposeFileSystem(handlers, options?)`** -- Worker-side counterpart from **`@taucad/runtime/filesystem`**; listens for the filesystem bridge connect envelope.

Call `dispose()` on either handle when the bridge is no longer needed.

## When to Use Each

| Constructor                  | Use when                                                    |
| ---------------------------- | ----------------------------------------------------------- |
| `fromNodeFs(basePath)`       | Node.js environment, disk-based projects, persistent cache  |
| `fromMemoryFs(files?)`       | Editor-driven content, tests, no disk I/O, ephemeral cache  |
| `fromFsLike(fs)`             | An already-rooted/confined virtual filesystem               |
| `fromBrowserFs(root)`        | Browser File System Access directory handle                 |
| `fromFileSystemBridge(open)` | Host-owned worker filesystem with a fresh rooted connection |

## Variations

- **Custom implementation**: Implement `RuntimeFileSystemBase` directly for custom backends (e.g., cloud storage, virtual mounts). See [API Reference: Filesystem](../api/filesystem) for the full interface.
- **Raw Node.js**: Use `fromNodeFs(hostRoot)`, not `fromFsLike`, so host paths are contained lexically and through symlink resolution.
- **Filesystem bridge**: For custom worker topologies, use **`createBridgePort`** from **`@taucad/rpc/bridge`** for generic object bridges and **`openFileSystemBridge`** / **`createFileSystemBridge`** from **`@taucad/fs-bridge`** for filesystem authorities. For opaque runtime transport wiring, prefer **`fromFileSystemBridge(openConnection)`** from **`@taucad/runtime/filesystem`**.
