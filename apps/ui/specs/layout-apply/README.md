# Layout apply: the arrangement record on Dockview

`LayoutApply.tla` models how the workbench arrangement record is applied to the two Dockview adapters. It is the spec for `workbench-layout.machine` (package A8a of the app state orchestration charter, decision D13, invariants I10 to I14, and the D18 claim about identical bytes). It lands before that machine, under formal verification policy rule 1.

The question it answers: with record publications, a person rearranging panes, pane intents, restore commands and Dockview mounting and unmounting, is the person's arrangement ever reverted, an intent ever lost or applied twice, a stale restore ever applied, or a revision acknowledged before it is on screen?

## Parties and abstraction

| Party       | State in the model                                                                                                                                                                                                                                                                                                                                                                                |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Record      | The latest publication from `recordSync`: its bytes, its attributed origin (own or foreign), whether an edit was counted since it arrived (`fresh`), whether it arrived while a local edit was unwritten (`held`) and whether its apply is done. Any bytes with any origin, so a misattributed echo of the store's own write is one of them. The applied revision is Unknown, `latest` or `older` |
| Arrangement | `shown`, one opaque value: what the attached adapters show. The edit count is kept through its comparisons (`fresh` on the record and on the apply in flight) and a ghost `edited` for the step that counts one. `sessions.writing`: a local edit is not yet written to the record                                                                                                                |
| Adapters    | Workbench and viewer, each `detached`, `attaching` or `attached`, and the workbench lane (`wbOpen`). A phone has the viewer only                                                                                                                                                                                                                                                                  |
| Intents     | Per id: `unsent`, `queued` for a target adapter, then `applied` or dropped with `routeChanged`, `workbenchClosed` or `unavailable`                                                                                                                                                                                                                                                                |
| Restore     | Commands `{id, expected, to}` from the arrange-workbench card, any number of them, with any expected arrangement (a repeated command is one whose arrangement moved); per id `applied` or `refused`                                                                                                                                                                                               |
| Session     | Today only: stores started and not disposed, and disposed stores whose write is in flight                                                                                                                                                                                                                                                                                                         |

Actions: `Published`, `PersonEdited`, `ApplyComputed`, `ApplyLanded`, `ApplyDiscarded`, `Acknowledged`, `AdapterAttaching`, `AdapterAttached`, `AdapterDetached`, `IntentSent`, `IntentApplied`, `IntentDropped` (`DropUnavailable`, `DropClosed`), `RouteKeyChanged`, `WorkbenchClosed`, `RestoreAsked`, `RestoreSettled`, `EditWritten`, and in `today` configurations only `HostRemounted`, `OldStoreDisposed` and `OrphanWriteLanded`.

`AdapterDetached` is a remount: the adapter detaches only while it has an attach cycle left, and attaches again. The workbench's last detach is `WorkbenchClosed`, which closes its lane whether its adapter is attached or between a remount's detach and attach. The viewer pane has no lane to close.

The model is untimed and its state is kept small on purpose. Only comparisons of the edit count and of revisions are observable, so the model keeps those comparisons instead of the numbers. `View` drops the ghosts, how a settled apply, intent or restore ended, a publication's origin (read only when it arrives), everything but the bytes of a publication whose apply is done, and everything of an apply in flight that can no longer land; no enabled action reads any of these (the module's comment on `View` gives the argument). `Symmetry` permutes the arrangements, which actions and properties only compare for equality. Neither is used by the liveness configuration.

## Properties

| Property                    | Invariant               | Statement                                                                                                                                                      | Form                                                                          |
| --------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `PersonEditNotReverted`     | I10                     | `ApplyLanded` never happens for an apply computed at an edit count lower than the current one                                                                  | action property: a landing apply is `fresh`                                   |
| `UnwrittenEditKept`         | I10 (A0.3 host I10 row) | No apply of a publication that arrived while a local edit was unwritten lands, including one that arrived at the current edit count                            | action property: a landing apply is not `held`                                |
| `IntentAccounted`           | I11                     | Every intent id is `applied` at most once, and leaves `queued` only by `IntentApplied` or by `IntentDropped` with a reason                                     | action property; a settled intent also stays settled                          |
| `RouteChangeDrops`          | I11                     | After `RouteKeyChanged`, every intent queued before it is `dropped{routeChanged}`                                                                              | action property on the step that changes the route key                        |
| `AckMeansApplied`           | I12                     | `Acknowledged(r)` only when an adapter is attached and the arrangement reflects `r`                                                                            | action property                                                               |
| `UnknownWhileDetached`      | I12                     | While no adapter is attached, the applied revision is `unknown`                                                                                                | invariant                                                                     |
| `SingleSession`             | I13                     | The number of record sessions for a file is at most one                                                                                                        | invariant                                                                     |
| `StaleRestoreRefused`       | I14                     | `RestoreSettled(id, applied)` only if the arrangement equals the command's `expected` at that step; otherwise it is `refused` and the arrangement is unchanged | action property                                                               |
| `IdenticalBytesHarmless`    | D18                     | A publication with the wrong `origin` and bytes equal to the current arrangement changes neither the arrangement nor the edit count                            | action property, checked for either origin                                    |
| `IntentEventuallyAccounted` | I11                     | Under weak fairness of the adapter, every intent becomes `applied` or `dropped` once an adapter stays attached and the route key stops changing                | liveness; antecedent `<>[]AnyAttached`; quiescence predicate `IntentsSettled` |
| `NoWriteAfterDispose`       | —                       | No disposed store still has a write in flight                                                                                                                  | invariant; witness only (`today-orphan-write`)                                |

How three statements are read:

- **"Computed at an edit count."** An apply carries the edit count at which its publication arrived (rule 2). "Lower than the current one" means an edit was counted since: the apply is not `fresh`.
- **"Bytes equal to the current arrangement."** Current when the publication arrives (the ghost `same`). The property covers the step it arrives in and the step an apply of it lands in. It is checked for both origins, so for the wrong one. Its arrangement half is checked evidence. **Its edit-count half is an assumption, not evidence**: only local changes (`Counted`) count an edit, and no publication or apply step is one, so it holds by construction. Rule 9 is what makes the assumption true in the machine.
- **"Once an adapter stays attached."** As the plan states it: any adapter. It holds because of rule 10 and the fairness of `Reattach`: a workbench intent whose adapter detached for a remount waits for the re-attach, and one whose lane closed is dropped `workbenchClosed`. The route key changes at most `MaxRoutes` times, so it always stops changing.

## Rules for A8a (`workbench-layout.machine`)

The target passes only because it keeps these rules. The machine must keep each one; `no-edit-count`, `no-unwritten` and `no-expected` show that rules 2, 8 and 5 are necessary.

1. Every local change of the arrangement counts one edit: a person's edit, an applied intent and an applied restore.
2. An apply carries the edit count at the step its publication arrived, not at the step it is computed. It lands only while its publication is still the latest and the count is unchanged; otherwise it is discarded. A newer publication supersedes an apply in flight.
3. An own publication whose bytes the arrangement already holds is not re-applied. Any other publication, own or foreign, is applied under rules 2 and 8; either may be acknowledged when the arrangement holds its bytes. (Today's host applies an own publication that is not stale, lines 203 to 263, and a reset is shown only through its own publication, line 396.)
4. A revision is acknowledged only while an adapter is attached, no apply is in flight and the arrangement holds its bytes. Any detach makes the applied revision unknown. When the last adapter detaches, an apply in flight is dropped and the latest publication's apply is computed again on the next attach.
5. A restore is a command `{id, expected}` that may repeat. It is settled against the arrangement at the step it settles: applied only if the arrangement equals `expected` and no local edit is unwritten (as `store.restore` refuses while an edit is owed), otherwise refused with nothing changed.
6. A route key change drops every queued intent with `routeChanged`, in the same step.
7. A workbench intent while the workbench lane is closed, or on a device with no workbench adapter, is dropped with `workbenchClosed`. Closing the lane drops the queued workbench intents the same way. An intent whose target does not open is dropped with `unavailable`.
8. A publication that arrives while a local edit is unwritten does not hold the edit, whatever edit count it arrived at. It is fenced at arrival and its apply never lands, even after the edit is written. The record's rebase of the edit (`recordSync`) comes back as a later publication, which rule 3 applies. In the machine: fence at the publication's arrival, never only at the landing.
9. An apply, and any adapter change event it causes, never counts as a person edit.
10. An adapter detaches either for a remount, after which it attaches again, or because its lane closes. An open lane's adapter re-attaches.
11. The record session is a runtime child that outlives any mount: no mount count, no second store for the file (I13).

Most of the state space is the product of independent parties (record, intents, restores, two adapters and their counters).

## Verdicts

- **All target configurations pass**, including `IdenticalBytesHarmless` now that own publications are applied under rules 2 and 8. An apply is a function of a publication's bytes, its edit count and whether it arrived over an unwritten edit, never of its origin, except that an own publication equal to the arrangement is not re-applied, which changes nothing either way. So a misattributed publication of the arrangement's own bytes changes nothing, and the `RecordSync` target-rule-1 tightening is not a dependency of A8b on this model's evidence. The edit-count half of the property is the assumption described above.
- **`today-store-replaced` fails `SingleSession`, a defect (inventory Y3), fixed by A8b.** `workbench-record-host.tsx` creates the layout store in `useMemo`, and `createWorkbenchLayoutStore` starts its `recordSync` actor at once. A remounted host therefore runs a second store from its render until the old one is disposed in the microtask after the effect cleanup (`storeMounts`, `queueMicrotask`, lines 28 and 400 to 410). TLC's shortest counterexample needs no write in flight: `HostRemounted` alone gives two sessions.
- **`today-orphan-write` fails `NoWriteAfterDispose`, a witness.** A write the old store had passed to `writeFileChecked` is not recalled by `dispose`: after the person edits, the host remounts and the old store is disposed, its write is still in flight, so the old store stays a writer of the file after the dispose (`OldStoreDisposed`, then `OrphanWriteLanded`).
- **`no-edit-count` fails `PersonEditNotReverted`.** A publication's apply is computed, the person edits, and the apply lands after the edit. The checker's shortest trace lands bytes equal to the edit, so it shows the landing the property forbids rather than a visible revert; a revert is the same trace with the edit to the other arrangement.
- **`no-unwritten` fails `UnwrittenEditKept`.** The person edits; a publication arrives after the edit, so at the current edit count, while the edit is still unwritten; its apply lands and the arrangement loses the edit. `PersonEditNotReverted` cannot see this, because the apply is `fresh`.
- **`no-expected` fails `StaleRestoreRefused`.** A single restore command whose expected arrangement is not the one shown is applied.

## Risks

- **One arrangement for two adapters.** `shown` stands for both adapters. Today `acknowledge` needs both the viewer and the workbench applied (lines 118 to 135). The model acknowledges when any adapter is attached and the one arrangement holds the bytes; A8a must not loosen today's rule to that.
- **Restore while an edit is owed.** The model refuses a restore while a local edit is unwritten, as `store.restore` does today; A8a must keep that refusal.

## Not modelled

- `recordSync` itself. `RecordSync.tla` is reused unchanged, and this model starts where its publications come out.
- The geometry of an arrangement, pane titles, the lanes, and what each adapter shows separately: an arrangement is one opaque value.
- The file-open dependency of a file pane: one "target available" flag, which the environment lowers at any step (`DropUnavailable`).
- The merge of an unwritten edit with a publication: rule 8 fences the publication; the rebased arrangement comes back as a later own publication.
- Restore is not in the graph export, which keeps the graph under 1 MB.
