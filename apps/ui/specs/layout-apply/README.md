# Layout apply: the arrangement record on Dockview

`LayoutApply.tla` models how the workbench arrangement record is applied to the two Dockview adapters. It is the spec for `workbench-layout.machine` (package A8a of the app state orchestration charter, decision D13, invariants I10 to I14, and the D18 claim about identical bytes). It lands before that machine, under formal verification policy rule 1.

The question it answers: with record publications, a person rearranging panes, pane intents, restore commands and Dockview mounting and unmounting, is the person's arrangement ever reverted, an intent ever lost or applied twice, a stale restore ever applied, or a revision acknowledged before it is on screen?

Actions: `Published`, `PersonEdited`, `ApplyComputed`, `ApplyLanded`, `ApplyDiscarded`, `Acknowledged`, `AdapterAttaching`, `AdapterAttached`, `AdapterDetached`, `IntentSent`, `IntentApplied`, `IntentDropped` (`DropUnavailable`), `RouteKeyChanged`, `WorkbenchClosed` (not on a phone), `RestoreAsked`, `RestoreSettled`, `EditWritten`, and in `today` configurations only `HostRemounted`, `OldStoreDisposed` and `OrphanWriteLanded`.

An **attach cycle** is one `AdapterAttaching` of an adapter, from `detached` to `attaching`. `MaxAttaches` bounds the attach cycles of each adapter, and so how often it can mount; detaches are not bounded. `AdapterDetached` is a remount's unmount, enabled in every state where the adapter is not detached, so an adapter can end detached once its cycles are spent. `WorkbenchClosed` closes the workbench lane, whether its adapter is attached or between a remount's detach and attach. The viewer pane has no lane to close. Only the liveness configuration sets `DetachGuard`, under which a detach or a lane close is enabled only while the adapter has an attach cycle left, so that environment assumption B can be honoured.

The model is untimed and its state is kept small on purpose. Only comparisons of the edit count and of revisions are observable, so the model keeps those comparisons instead of the numbers. `View` drops the ghosts `act` and `edited`, the `gh` ghosts where they repeat what it drops, how a settled apply, intent or restore ended, a publication's origin (read only when it arrives), everything but the bytes of a publication whose apply is done, and everything of an apply in flight that can no longer land, which is kept as a `dead` value distinct from every live apply (a live apply of the same bytes is not merged with it). Each dropped part is read by no enabled action, and by a property only in the step that sets it, so two states with the same view have the same behaviours, with or without `Symmetry` (the module's comment on `View`). `Symmetry` permutes the arrangements, which actions and properties only compare for equality. Neither is used by the liveness configuration.

How three statements are read:

- **"Computed at an edit count."** An apply carries the edit count at which its publication arrived (rule 2). "Lower than the current one" means an edit was counted since: the apply's `gh.applyUnt` is FALSE. `gh.recUnt` and `gh.applyUnt` are ghosts with the same values as rule 2's `fresh` (set at a publication's arrival, copied by `ApplyComputed`) that no guard reads, and each local change (`PersonEdited`, `IntentApplied`, an applied restore) clears them as its own conjunct, not through `Counted`; so the property does not restate the guard, and a local change that does not count its edit is caught by it. Likewise `UnwrittenEditKept` reads `over`, not rule 8's `held`, and `IntentAccounted`'s "at most once" reads `gh.applications`, which `IntentApplied` increments itself. Each target property is caught alone by a mutant of its own mechanism (see Mutants).
- **"Bytes equal to the current arrangement."** Current when the publication arrives (the ghost `same`). The property covers the step it arrives in and the step an apply of it lands in. It is checked for both origins, so for the wrong one. Its arrangement half is checked evidence. **Its edit-count half is an assumption, not evidence**: only local changes (`Counted`) count an edit, and no publication or apply step is one, so it holds by construction. Environment assumption A is what makes it true in the machine.
- **"Once an adapter stays attached."** As the plan states it: any adapter. A phone is checked by `liveness-phone`, since its fairness differs (assumption B). Under `LiveSpec` the antecedent `<>[]AnyAttached` always holds: with `DetachGuard` every detach leaves an attach cycle, and weak fairness of `Reattach` and `AdapterAttached` (assumption B) brings the viewer back each time, so the property is checked on every fair behaviour. It holds because of rule 7 and assumptions B and C: a workbench intent whose adapter detached for a remount waits for the re-attach, a file intent whose lane closed is dropped `workbenchClosed`, and a pane intent whose lane closed waits for the lane to reopen (assumption C). The route key changes at most `MaxRoutes` times, so it always stops changing.

## Rules for A8a (`workbench-layout.machine`)

The target passes with these rules, under the environment assumptions below. The machine must keep each rule; `no-edit-count`, `no-unwritten` and `no-expected` show that rules 2, 8 and 5 are necessary to the properties. Three parts are as-built rules that no property needs, kept so that the model matches today's host: rule 4's "no apply in flight" before an acknowledgement, rule 5's refusal of a restore while a local edit is unwritten, and rule 3's apply of an own publication whose bytes differ from the arrangement.

1. Every local change of the arrangement counts one edit: a person's edit, an applied intent and an applied restore.
2. An apply carries the edit count at the step its publication arrived, not at the step it is computed. It lands only while its publication is still the latest and the count is unchanged; otherwise it is discarded. A newer publication supersedes an apply in flight.
3. An own publication whose bytes the arrangement already holds is not re-applied. Any other publication, own or foreign, is applied under rules 2 and 8; either may be acknowledged when the arrangement holds its bytes. (Today's host applies an own publication that is not stale, lines 203 to 263, and a reset is shown only through its own publication, line 396.)
4. A revision is acknowledged only while every adapter of the device is attached (on a phone, only while the editor tab shows the workbench), no apply is in flight and the arrangement holds its bytes. Any detach makes the applied revision unknown. When the last adapter detaches, an apply in flight is dropped and the latest publication's apply is computed again on the next attach.
5. A restore is a command `{id, expected}` that may repeat. It is settled against the arrangement at the step it settles: applied only if the arrangement equals `expected` and no local edit is unwritten (as `store.restore` refuses while an edit is owed), otherwise refused with nothing changed.
6. A route key change drops every queued intent with `routeChanged`, in the same step: the file intents and a handed-back pane intent (`project-workspace-context.tsx` line 240). A pending record edit (a pane change held before the first read or written to the record) is not an intent. It survives a route change, since `WorkbenchRecordHost` is not keyed to the route (`project-live-sessions.tsx` line 660), only while the first read succeeds: if the read fails or is refused, `unapplied()` hands the edit back (`workbench-record-host.tsx` lines 570 to 574), and if the route changed meanwhile the hand-back is dropped with no reason (`project-workspace-context.tsx` lines 389 to 391; A0.3 row 1b 'before', `project-workspace-context.test.tsx` lines 1073 to 1109). A8a must record that drop as `routeChanged` (I11), and otherwise must not drop a pending record edit: that would revert edits the person already wrote (D14, I10).
7. On a device with a workbench, a workbench intent opens the workbench lane, as `openPanel` and the `fileOpened` listener call `setWorkbenchOpen(true)` today (`project-workspace-context.tsx` lines 375 and 545). On a phone it switches to the editor tab instead (lines 535 to 543: the open is kept as `pendingUserFileRef` and `mobileActiveTab` becomes `editor`), and the intent is applied once the workbench attaches (lines 426 to 432). Closing the lane drops the workbench `file` intents queued at that step with `workbenchClosed`, as today's close clears the held Files and user-file intents (lines 338 to 341). A queued `pane` intent (the handed-back slot) survives the close and is applied exactly once when a workbench next attaches: A0.3 row 1c (`project-workspace-context.test.tsx` lines 1111 to 1139, `openPanel('share')`, `record.handBack()`, then `setWorkbenchOpen(false)`), a guard A8a must keep green. A pending record edit is not an intent and survives the close (rule 6 for the route change); a phone has no lane to close, and leaving the editor tab only detaches the workbench. An intent whose target does not open is dropped with `unavailable`.
8. A publication that arrives while a local edit is unwritten does not hold the edit, whatever edit count it arrived at. It is fenced at arrival and its apply never lands, even after the edit is written. The record's rebase of the edit (`recordSync`) comes back as a later publication, which rule 3 applies. In the machine: fence at the publication's arrival, never only at the landing.
9. The record session is a runtime child that outlives any mount: no mount count, no second store for the file (I13).

## Environment assumptions

These are assumptions about Dockview and the adapters, not obligations of the machine. The model relies on them; A8a's tests should state them where they can be observed.

- **A. An apply never counts as an edit.** An apply, and any adapter change event it causes, is not reported as a person's edit. In the model only `Counted` steps count one, so `IdenticalBytesHarmless`'s edit-count half holds by construction.
- **B. An open lane's adapter re-attaches.** On a desktop an adapter detaches either for a remount, after which it attaches again, or because its lane closes. On a phone the workbench also detaches when the person leaves the editor tab, and only a workbench intent switches back to it (`project-workspace-context.tsx` lines 535 to 543), so B there is narrower: the workbench attaches again while a workbench intent is queued. The person is not assumed to return to the tab otherwise. In the model this is weak fairness of `Reattach` (on a desktop, a detached adapter whose lane is open attaches; on a phone, the viewer always and the workbench while `WorkbenchQueued`) and of `AdapterAttached`, used only by `liveness` and `liveness-phone`, together with `DetachGuard`. See Risks for the case B leaves out.
- **C. A closed lane holding a queued pane intent is reopened eventually.** Today nothing reopens it: the person does, by opening the workbench again. In the model this is weak fairness of `Reopen` (the workbench lane reopens and the workbench attaches while a pane intent is queued), used only by `liveness`. It is an assumption, so that `IntentEventuallyAccounted` keeps the plan's antecedent; without it, a pane intent behind a closed lane stays queued (a mutant shows this).

## Verdicts

- **All target configurations pass**, including `IdenticalBytesHarmless` now that own publications are applied under rules 2 and 8. An apply is a function of a publication's bytes, its edit count and whether it arrived over an unwritten edit, never of its origin, except that an own publication equal to the arrangement is not re-applied, which changes nothing either way. So a misattributed publication of the arrangement's own bytes changes nothing, and the `RecordSync` target-rule-1 tightening is not a dependency of A8b on this model's evidence. The edit-count half of the property is the assumption described above.
- **`today-store-replaced` fails `SingleSession`, a defect (inventory Y3), fixed by A8b.** `workbench-record-host.tsx` creates the layout store in `useMemo`, and `createWorkbenchLayoutStore` starts its `recordSync` actor at once. A remounted host therefore runs a second store from its render until the old one is disposed in the microtask after the effect cleanup (`storeMounts`, `queueMicrotask`, lines 28 and 400 to 410). TLC's shortest counterexample needs no write in flight: `HostRemounted` alone gives two sessions.
- **`today-orphan-write` fails `NoWriteAfterDispose`, a witness.** A write the old store had passed to `writeFileChecked` is not recalled by `dispose`: after the person edits, the host remounts and the old store is disposed, its write is still in flight, so the old store stays a writer of the file after the dispose (`OldStoreDisposed`, then `OrphanWriteLanded`). The witness stands only for a write already on the wire. The model's `writing` does not tell an owed, debounced edit from a sent write, but the old store never sends an owed edit after its dispose: `dispose` closes the record (`workbench-layout-controller.ts` lines 223 to 228), the write port answers `ineligible` once disposed (line 143), and the close fence keeps edits no write has taken owed and publishes nothing after the close (`record-sync.machine.ts` lines 878 to 890). That owed edit is lost instead; see Risks.
- **`no-edit-count` fails `PersonEditNotReverted`.** A publication's apply is computed, the person edits, and the apply lands after the edit. The checker's shortest trace lands bytes equal to the edit, so it shows the landing the property forbids rather than a visible revert; a revert is the same trace with the edit to the other arrangement.
- **`no-unwritten` fails `UnwrittenEditKept`.** The person edits; a publication arrives after the edit, so at the current edit count, while the edit is still unwritten; its apply lands and the arrangement loses the edit. `PersonEditNotReverted` cannot see this, because the apply is `fresh`.
- **`no-expected` fails `StaleRestoreRefused`.** A single restore command whose expected arrangement is not the one shown is applied.

## Risks

- **One arrangement for two adapters.** `shown` stands for both adapters. Today `acknowledge` needs both the viewer and the workbench applied (lines 118 to 135), and the model now requires every adapter of the device attached (`AckNeedsEveryAdapter`, D14); on a phone the acknowledgement waits until the editor tab shows the workbench. The model still cannot tell the two adapters' arrangements apart, so "applied" means attached with the one arrangement holding the bytes.
- **The viewer seeded from the stored record.** Today `registerViewer` seeds the viewer with `store.snapshot().layout` (line 497), the stored record, while the workbench gets `intendedLayout()` (lines 522 to 526). A viewer that attaches while a person edit is unwritten shows the stored arrangement, not the edit. This is already true on `main`, and programme control ruled it an A8b risk, not a rule of A8a. The model does not check it: an attach never changes `shown` (see Not modelled), so a mutant that seeds from the record passes.
- **A debounced edit lost at a remount.** A layout edit still debounced (about 500 ms) when the host remounts is dropped at the old store's dispose and never written by it (the close fence above), and the new store does not hold it. This is already true on `main`, and the model does not show it, since its `writing` is one flag. A8b must check it: the single runtime session outlives the mount, so the edit should be written.
- **One pane intent in the slot at a time.** Today `pendingPreviewPanel` holds one entry, so a second pane intent held there (handed back at line 395, or opened in pane mode at line 364 of `project-workspace-context.tsx`) before a workbench connects silently overwrites the first. This is true on `main` and an I11 gap for A8b; the model queues both.
- **Pending record edits partly rest on reading the code.** Row 1c guards the handed-back source, and A0.3 row 1b 'before' (`project-workspace-context.test.tsx` lines 1073 to 1109) pins the refused-read branch: the edit is handed back and, after a route change, dropped silently at `project-workspace-context.tsx` lines 389 to 391 (an I11 gap: no `routeChanged` is recorded). Only the success branch, where the edit is applied after the read and shown on the next attach across a lane close or route change, has no test; it rests on reading `workbench-record-host.tsx` lines 564 to 610 and `project-live-sessions.tsx` line 660. A8b or A8a should pin it with an A0.3-style row.
- **Plain node changes before the first read.** Before the first read, `personWorkbenchChanged` keeps only function changes (`workbench-record-host.tsx` lines 565 to 595); a plain node change is discarded with nothing recorded. This is true on `main`, an I10 area the model does not cover.
- **A pane intent behind a closed lane.** Today a pane intent kept through a lane close waits until the person reopens the workbench, indefinitely if they never do. The model assumes the reopening (assumption C); A8a should state what happens otherwise.
- **A phone intent left behind.** Assumption B on a phone has the workbench attach while a workbench intent is queued. If the person leaves the editor tab with the intent queued and never returns, today the intent stays queued as `pendingUserFileRef` until the route key changes. A8a should state what happens then.
- **A lane close on a phone.** Closing the last workbench pane on a phone calls `setWorkbenchOpen(false)` (`chat-workbench-dockview.tsx` line 2069), which clears the queued placements as a desktop lane close does. The model has no lane close on a phone (`Phone` disables `WorkbenchClosed`); A8a must decide whether this is a lane close with `workbenchClosed`.
- **Intents cleared with no reason.** Today `openPanel` clears `pendingUserFileRef` and `pendingFilesRef` with no recorded reason (`project-workspace-context.tsx` lines 352 to 358). That is true on `main` and is an I11 gap for A8b: every dropped intent needs a reason.
- **The export graph is narrow.** The `export` graph has the viewer only and no restore, so A8a's replay of it does not exercise the workbench, `WorkbenchClosed`, rule 7 or restore. Those rest on the TLC configurations alone.
- **No acknowledgement with the workbench lane closed.** On a desktop with the workbench lane closed, no revision is ever acknowledged, because today's `acknowledge` needs both adapters applied (lines 118 to 135), and so does the model's (rule 4). This is true on `main`; A8a must decide what a closed lane means for D14.
- **A second silent intent drop.** `project-workspace-context.tsx` lines 426 to 432: the file opener claims `pendingUserFileRef` and activates it only if the file is in `openFiles`; otherwise the intent is dropped with no reason. This is true on `main`, the same I11 gap carried to A8b as the `openPanel` clears.
- **Restore while an edit is owed.** The model refuses a restore while a local edit is unwritten, as `store.restore` does today; A8a must keep that refusal.

## Not modelled

- Pending record edits: a pane change held before the first read or written to the record belongs to the record session, not the intent queue (rules 6 and 7). It survives a lane close, and a route change only while the first read succeeds; the model has neither branch.
- How an attaching adapter is seeded. An abstraction: an attach never changes `shown`, so every adapter is seeded with the arrangement. Today's viewer is seeded from the stored record instead (`workbench-record-host.tsx` line 497), which is the A8b risk recorded above.
- `recordSync` itself. `RecordSync.tla` is reused unchanged, and this model starts where its publications come out.
- The geometry of an arrangement, pane titles, the lanes, and what each adapter shows separately: an arrangement is one opaque value.
- The file-open dependency of a file pane: one "target available" flag, which the environment lowers at any step (`DropUnavailable`).
- The merge of an unwritten edit with a publication: rule 8 fences the publication; the rebased arrangement comes back as a later own publication.
- A debounced edit apart from a sent write (see Risks).
- Restore is not in the graph export, which keeps the graph under 1 MB. `AdapterDetached` is in it.

## Graph, suite and drift

`expected.json` has a `graphs` entry for `LayoutApply` with `export` and the phase `applied`. `LayoutApply/graph.json` is the reachable graph of `export`, and `LayoutApply/suite.json` the covering suite. `LayoutApply/drift.json` ties this module to `workbench-layout.machine`: `apps/ui/app/workbench-records/workbench-layout.machine.conformance.test.ts` checks the manifest with the machine's alphabet, version and `meta.tla` actions, replays the covering suite and 400 seeded walks of the `export` graph, and checks the action correspondence (MC-R27).

Regenerate with `node tools/formal/src/cli.ts update apps/ui`.

## Running

Every configuration but `wide` and `target-phone` is in the `pr` tier and runs in this family's own target, `ui:formal:tla:layout-apply`, which CI runs in parallel with ui's other families (formal verification policy § 6): about 45 s wall at the runner's flags, with the SANY parse and the graph and suite freshness check, which exports the `export` graph through TLC in a few seconds. `wide` (about 140 s) and `target-phone` (about 250 s) are `nightly` and run in `ui:formal:wide` on its schedule. The drift test runs with the ui tests.

pnpm nx run ui:formal:tla:layout-apply                   # SANY, the pr configurations, graph and suite
