# Library catalog: discovery, recovery and route access

`LibraryCatalog.tla` models one tab's project library: discovery passes and their epoch, the mutations this tab makes, the journal of pending operations and its recovery loop, and the questions a route asks about one project's access. It is the spec for `library-discovery.machine`, `library-recovery.machine` and `library-access.machine` of the app state orchestration charter (D10, D13; invariants I4, I7, I8, I9 and I18), and it lands before them, under formal verification policy rule 1. The `today` configurations describe `apps/ui/app/hooks/use-project-manager.tsx` as it was at `7918b118`, before A3b wired the machines into `ProjectLibrary` (`apps/ui/app/runtime/project-library.ts`); its line citations below are to that commit. `LibraryCatalog/drift.json` hashes both files, so a change to either is reviewed against this spec.

## Parties and abstraction

| Party      | Model                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage    | The set of project roots and the journal, a set of rows `{id, operation, project}` (`rowProj`, `rowOp`). Durable: a `Crash` keeps both                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Other tabs | The environment. They change a root (`EnvChangedStorage`), add a row (`EnvAddedRow`) and settle a row (`EnvSettledRow`) at any step. This tab hears of a root change through its watch (inventory L1), modelled as an invalidation in the same step. It sees another tab's row only when it reads the journal, which it does at start and after a `Crash`                                                                                                                                                                                                                                                                                                                         |
| Discovery  | One pass at a time (`PassStarted`, `PassSettled`). A pass starts when one is owed, or when a poll or a route's read asks for one (`MaxPolls`). The scan sees storage when the pass starts. Every pass and every invalidation (`EpochBumped`, a replay settling, a discard, a storage change, the workspace leaving or returning) moves the epoch. During a write stop a pass publishes what it read and skips its writes (`skipped`). The pass's epoch and listing are the discovery machine's context (inventory L2, L5)                                                                                                                                                         |
| Recovery   | One record per row this tab has seen: `unseen`, `waiting`, `replaying`, `recovered`, `failed` or `discarded`, with the attempt count and the failure reason (`terminal` or `workspace`). The recovery loop replays one journal row at a time; a mutation's own row settles beside it. The attempt count is volatile: a `Crash` reloads every journal row as `waiting` with no attempts                                                                                                                                                                                                                                                                                            |
| Mutations  | `MutationJournaled(p, o)`: a create or delete from this tab writes its row and starts applying it. A request the gate refuses is asked again later, so the model admits it only once the gate is open. Its settle is `ReplaySettled`, labelled `MutationApplied`                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Workspace  | `available` or `unavailable`. While it is away a read of storage sees nothing (`Visible`) and every replay fails with `workspace-unavailable`. Its return (a re-pick, heard through the cross-tab root-configuration subscription, inventory L6) re-arms those rows. Today two more triggers replay them whether or not it has returned, every root-configuration message (`use-project-manager.tsx` 2156 to 2172) and every `prepareCurrentWorkspaceCatalog` (2861 to 2867); under programme control's ruling both are named changes in A3a that wait for the workspace (rule 6; A0.4's red `RetryOnlyWhenCleared` row). `createProject(id)` is the one replay outside the model |
| Access     | Questions `{id, project}` with a generation (`AccessAsked`; inventory L8). Asking again or cancelling (`AccessCancelled`, at most `MaxAsks` times) replaces the question and moves its generation. The top of the loop reads the recovery set with no await; each of the `Reads` reads sends a reply tagged `{id, gen}` (`AccessRead`) that completes later (`AccessReadDone`), possibly after the epoch or the recovery set moved, after the question was replaced, or after a `Crash`. A reply that matches no reading question is dropped (`AccessStaleReply`). An answer is `AccessAnswered`; a question that must read again is `AccessReread`                               |

**Epochs.** The model keeps no epoch counter. Every value stamped with an epoch (the pass in flight, the listing on its way to the query cache, an open question's reads) carries `cur`, true while its epoch is still the current one. A pass or an invalidation clears every `cur`. That is all an epoch comparison reads, and it keeps two runs that differ only in how far the counter got from being two states. A question's `rs` records that a recovery row for its project started since its first read.

**Abstracted away.** What an operation writes beyond the root it adds or removes (a rename is a write that changes no root, so it is left out); thumbnails and metadata refresh; cloud projects; the workspace connection handshake; the 5 s poll, the observation debounce and every worker round trip, which are steps; the discovery-before-replay ordering at bootstrap; the trashed, conflict and route-blocked answers, which come from the same fenced reads as `ready` and `missing`; locks. The model specifies no lock and adds none. Only project creation takes a named lock today, and that is preserved.

## Properties

| Property                 | Kind                 | Statement                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------ | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NoStaleReconcile`       | action               | I7. The catalog is replaced only by a pass whose epoch equals the current epoch                                                                                                                                                                                                                                                                                                                                                                     |
| `RecoveryGatesMutation`  | action               | I8. A mutation on project `p` is not journaled while this tab holds a row for `p` in `waiting` or `replaying`                                                                                                                                                                                                                                                                                                                                       |
| `RowAccounted`           | invariant and action | I8. Every row this tab has seen is in exactly one state and leaves them only when the tab reloads. A row becomes failed only on a terminal reason, on workspace-unavailable, or on its third settled attempt (this wording is ruled by programme control), and `discarded` only by `PersonDiscarded`, which removes its journal row and nothing else                                                                                                |
| `TerminalStops`          | action               | I8. No `ReplayStarted(row)` follows a terminal failure of that row, in this tab                                                                                                                                                                                                                                                                                                                                                                     |
| `RetryOnlyWhenCleared`   | action               | I8. A row that failed with `workspace-unavailable` (a `failed` row whose reason is `workspace`) is replayed again only after `WorkspaceReturned`                                                                                                                                                                                                                                                                                                    |
| `SkippedPassRedone`      | invariant            | I9. If a pass was skipped during a write stop, a pass starts after the stop ends and before the catalog is reported current (`ReportedCurrent`)                                                                                                                                                                                                                                                                                                     |
| `CatalogReflectsStorage` | invariant            | I7. When no pass, listing, mutation or replay is in flight and the epoch is settled, the catalog equals storage as a read of it sees it. The environment acts in single steps, so it is quiet in every state                                                                                                                                                                                                                                        |
| `AccessAnswerFenced`     | action               | I4, D10. An answer is delivered only for the current epoch, from reads all taken at it, with no recovery row for the project started since the first of them; otherwise the question is read again. An answer is `recovering` or `recovery-failed` exactly when this tab holds such a row                                                                                                                                                           |
| `AccessMatchedById`      | action               | I18. A reply that changes a question changes only its own question (same id), and only while that question is reading under the reply's generation and about the reply's project, so a reply sent before a crash changes nothing. An answer is delivered at most once per question `{id, gen}` (`deliveries`), to the question open under that id and generation. Whether an answer is still true is `AccessAnswerFenced`'s concern, not this one's |
| `RowEventuallySettled`   | liveness             | Under weak fairness of the replay and of discovery, once the workspace stays available, every row this tab has seen becomes `recovered`, `failed` or `discarded`. Quiescence predicate: `RowsQuiescent`. The environment is bounded, so it falls quiet                                                                                                                                                                                              |
| `SingleReplay`           | witness              | A row this tab replays is still in the journal. It is not a property the design enforces: `env-double-replay-witness` shows that its violation is reachable                                                                                                                                                                                                                                                                                         |

`RowAccounted` conjoins an invariant with an action formula, so TLC reports a violation of it by location, not by name: a future configuration expected to violate it would show up as an `error`, and would need the two parts split.

"In this tab" scopes `RowAccounted`, `TerminalStops` and `RetryOnlyWhenCleared` to one life of the tab: a `Crash` forgets every in-memory failure and attempt count. The journal row holds no failure reason, so after a reload the tab replays a row that failed before it, terminally or for the workspace, as it does today.

## Rules the machines keep (A3a)

`target`, `target-environment`, `target-workspace`, `target-access`, `target-access-crash`, `today-ref-epoch-safe`, `env-double-replay` and `liveness` check these. `library-discovery`, `library-recovery` and `library-access` implement them.

1. **One epoch for every listing.** Starting a pass and every invalidation move the epoch. A pass applies its listing in the same transition that compares the pass's epoch with the current one, and drops it otherwise. Nothing between the comparison and the catalog write may yield (`no-epoch` and `today-ref-epoch` show why).
2. **An invalidation owes a pass.** A replay settling, a discard, a root change heard through the watch, the workspace leaving or returning, and the end of a write stop after a skipped pass all move the epoch and owe a pass, so the catalog equals storage once nothing is in flight.
3. **A write stop is remembered.** A pass that settles during a stop records that it skipped its writes. When the stop ends after one, the machine invalidates and owes a fresh pass, and reports the catalog current only once no pass is owed or in flight.
4. **Recovery gates mutation.** A mutation on a project is refused, or waits, while the tab holds a waiting or replaying row for it. A failed, recovered or discarded row does not gate. Today `createProject(id)` first settles any unfinished row for that id, another tab's included, under its named lock (`use-project-manager.tsx` 2313 to 2333); the model leaves that path out with the lock. It is also a replay outside the recovery loop (rule 6).
5. **Every row is accounted for.** One state per row this tab has read from the journal. A row becomes failed only on a terminal reason, on workspace-unavailable, or on its third settled attempt. A terminal reason (`identity-conflict`, `filesystem-error`, `local-state-error`) fails it and it is never replayed again in this tab. Only the recovery loop counts attempts: `settleRecovery` counts one before each replay and makes no fourth (`use-project-manager.tsx` 2102 to 2109). A mutation applying its own row (create, duplicate and permanent delete settle through `resumePendingProjectOperation`, 1804, 2695 and 3187) counts none, so its row starts with no attempts (D14). Only the person discards: the library offers Discard on a failed row only (`project-library.tsx` 686), though `discardRecovery` itself checks no status. Attempts are counted in memory. With the current reasons every failure is terminal or `workspace`, so `RowAccounted`'s third-attempt clause is never the only reason a row fails; it stays for a retryable reason added later.
6. **Workspace failures wait for the workspace.** A row that settles with `workspace-unavailable` is `failed` with that reason and keeps the attempts it has: none for a mutation's own settle (`resumePendingProjectOperation`, 1619 to 1624), the one just counted for a replay (`settleRecovery`, 2098 to 2102), so a route asking about its project answers `recovery-failed` (2441 to 2443) and the person may discard it. When the workspace returns, every such row with fewer than three attempts is replayed again (`retryFailedRecoveries`, 2116 to 2131), and the recovery loop replays it at no other time. `settleRecovery` skips only a terminal row or one with three attempts (2081 to 2086), so every caller of it replays a `workspace-unavailable` row and counts an attempt, whether or not the workspace has returned. Today two triggers call it through `retryFailedRecoveries` with no workspace check:
   - Every cross-tab or desktop root-configuration message (`subscribeProjectRootConfigurationChanges`, `handle-store.ts` 127), whose listener calls `retryFailedRecoveries` (2135 to 2151), not only the one a re-pick sends.
   - Every `prepareCurrentWorkspaceCatalog` (2840 to 2846), which calls `retryFailedRecoveries` first. It is reached through `refreshWorkspaceCatalog`, `repairWorkspaceBindings` and the connection machine's `prepareWorkspaceCatalog`, including right after a workspace disconnects (`workspace-connections.tsx` 214).

   Programme control has ruled that both are named changes in A3a: each replays a `workspace-unavailable` row only after `WorkspaceReturned` or a workspace check shows the workspace is present. A0.4's red `RetryOnlyWhenCleared` row pins today's behaviour ("retryFailedRecoveries on a root-configuration announcement with no workspace check"). The target models the ruled design as it is: `WorkspaceReturned` is the only step that re-arms such a row, and it fires only when the workspace becomes available.

   One replay stays outside the model, kept as today under D14: `createProject(id)`, which under its named lock calls `settleRecovery` on the project's unfinished row (2302 to 2306). Programme control has ruled that it is a replay the person asks for, not an automatic retry, so `RetryOnlyWhenCleared` does not cover it. Today `retryFailedRecoveries` settles those rows in a loop of its own, which can overlap the startup recovery loop; the model replays one row at a time, and A3a should name that difference when it implements the retry.

7. **Replays run one at a time** in the recovery loop. A mutation's own row settles beside them.
8. **Access answers are fenced.** At the top of each turn a held row answers `recovering` (waiting or replaying) or `recovery-failed`. Otherwise every read records the epoch it observed: for a discovery pass, the pass's own epoch, as today (`discoveryPassEpochRef`, 2477 to 2479), not the epoch before that pass started, which the pass itself moves and which would make the loop read again forever. After the last read the answer is delivered only if the epoch has not moved since the first read observed it, no recovery row for the project started since then and none is held. Otherwise the question reads again from the top. This applies to every answer, `missing` and `unavailable` included (`today-access-loop` shows the gap when it does not).
9. **Answers are matched by id and generation.** Asking again or cancelling moves the question's generation. Every read is tagged `{id, gen}`, and a reply counts only while its question is reading under that generation; any other reply, late from a replaced, cancelled or pre-crash question, is dropped and changes no question. A reply reads the project it was sent for. One answer per `{id, gen}` (`access-match-by-id` shows a reply matched by id alone, from a read of p1, answering the question asked again about p2).

The model specifies no lock. Two tabs may replay one row at once (OQ6); that is the inherited risk `env-double-replay-witness` reports. When it happens, this tab still settles its own replay and accounts for the row (`env-double-replay`).

**Tiers.** Every configuration but `wide` is in the `pr` tier and runs in this family's own target, `ui:formal:tla:library-catalog` (about 80 s at the runner's flags), which CI runs in parallel with ui's other families (formal verification policy § 6). `wide` is `nightly` and runs in `ui:formal:wide` on its schedule.

`expected.json` states each configuration's bounds. Sized for the `pr` queue, the configurations other than `target`, `liveness`, `target-access-crash` and `today-access-loop` leave out the crash, and all but `target` and `wide` leave out the write stop. `target-workspace` keeps one mutation and `target-access` drops the crash; their refs in `expected.json` say what each drops. No access configuration loses the workspace, so `unavailable` answers and rule 8's pass-epoch reading (an access read that is a discovery pass) are not modelled; the first read is a plain storage read.

**`wide` is narrowed.** The formal plan states 3 projects, 3 mutations, 2 crashes, 2 environment steps and 2 access questions. `wide` checks every property at 3 projects, 1 row at start, 2 mutations, 1 crash and 1 write stop with a quiet environment: 2,531,500 distinct states in about 90 s at the nightly tier. Probed beyond it, each of these exhausted the runner's 1 GB heap or hit its 900 s watchdog: that configuration plus one journal row another tab writes (4 rows); that configuration plus one root another tab changes; 3 projects with 3 mutations and 1 crash, with or without a fourth row; 3 projects, 4 rows, 3 mutations and 2 crashes; 3 projects with 2 mutations, 2 crashes and 2 environment steps; 3 projects with 2 mutations, 1 crash, 2 environment steps and 2 access questions; 3 projects with 2 mutations, 1 crash and a root change and settle by another tab; 2 projects with 2 mutations, 1 crash, 1 write stop and 2 environment steps, with or without a workspace loss. The environment and access questions are each checked in a configuration of their own instead. No configuration has a second crash (`MaxCrashes = 2`): that is an accepted narrowing.

### What the `today` configurations found

- **`today-ref-epoch`** fails `NoStaleReconcile` in five steps: a pass settles at the current epoch and `getProjectListing` returns its listing; a poll starts the next pass, which moves the epoch; the earlier listing then lands in the query cache. Every invalidation that follows a storage change also cancels the `projects` query, so the listing that lands is the one storage still holds: the window breaks the epoch rule, not the catalog's contents (`today-ref-epoch-safe` checks `CatalogReflectsStorage` and every other property under the same fence). Recorded as a witness.
- **`today-access-loop`** fails `AccessAnswerFenced` in seven steps: a route asks about a project that is not on disk; its first read starts; a creation of that project with a supplied id (a Tau Cloud open racing materialize, say) puts its row in the recovery set, which moves no epoch until the commit ends; both reads complete at the same epoch, and the loop answers `missing` while the tab holds a recovering row for the project. The found path re-checks the recovery set (`recoveryStarted()`), but the paths that answer `missing`, `unavailable` or `conflict` check only the epoch. The answer is corrected when the creation's invalidation reaches the route. Recorded as a defect that A3a fixes (rule 8).

## Generated files

- **Graph and suite.** `expected.json` has a `graphs` entry for `LibraryCatalog` with `export` and the phase `pass.st`. `LibraryCatalog/graph.json` is the reachable graph of `export` and `LibraryCatalog/suite.json` its covering suite. `export` has `MaxAsks = 0` and `MaxBumps = 0`, so the suite has no `AccessCancelled`, `AccessStaleReply` or `EpochBumped` step: A3a's I18 generation matching is checked by the model configurations above and by machine tests, not by suite replay. `library-catalog.conformance.test.ts` replays the suite on the three machines, wired as the library service will wire them, and checks that every `meta.tla` names an operator of this module.
- **Drift.** `LibraryCatalog/drift.json` holds the hashes of this module, its configurations, `expected.json` and `use-project-manager.tsx`. It also holds the alphabets, versions and `meta.tla` actions of `library-discovery`, `library-recovery`, `library-access` and its query child, and the hashes of their files. `library-catalog.drift.test.ts` fails when any of them moves without the manifest.

Regenerate with `node tools/formal/src/cli.ts update apps/ui`.
