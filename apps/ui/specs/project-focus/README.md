# Project focus

`ProjectFocus.tla` checks which project has focus when the person navigates between projects faster than a leave flush, an access check or the project runtime import completes. It answers the formal plan's ProjectFocus question for the focus machine and its route-state selector, which lane A5a builds (`Focus = "target"`). It also models `ProjectRouteGate` as built at `c5f528dd` (`Focus = "today"`), so that the defects the inventory names, U1, U13 and U20, are counterexamples of the same properties.

## Parties

| Party           | In the model                                                                                                                                                                                                                             |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Router          | `route`, the newest committed request `{id, project, chat}`, or `Home`. `RouteCommitted` and the focus step that hears it are separate, so the selector sees a commit before focus does                                                  |
| Library         | An epoch that `LibraryChanged` moves and one access answer per project, `ready` or `held` (every held kind is one value). It answers for the epoch current when it answers; the epoch may move before focus acts on the answer           |
| Focus           | `f`: its request, `idle`, `resolving`, `leaving`, `opening`, `focused`, `held` or `flushFailed`, the answer it holds, the session it is on and the one it is leaving with that session's leave flush                                     |
| Module          | `mod`, the project runtime import, one for every project                                                                                                                                                                                 |
| Registry        | `sess`, `sreq`, `pendingOpen`: the live set, the budget, the single `pendingOpen` slot and the request it keeps, each session's close flush, and idle expiry. This is environment: the model claims no conformance of `sessions.machine` |
| Opening session | `fact`: once live it reports its chat session and its first file check, and one open bound may pass while either is pending                                                                                                              |
| Person          | Edits the project whose editor is shown, opens a project from the sidebar or a notice (through focus), closes a project and retries (through their owners)                                                                               |

The registry answers an open in the step that sends it, as the actor does, so `OpenAsked` is also `OpenSettled`. `Touch` and the registry's recency order are not modelled, so a policy close may take any candidate.

## Rules the focus machine keeps (A5a)

The target actions are the rules. A machine that keeps them inherits the properties above.

1. **Request and selector.** A request is `{id, project, chat}`. The selector reads the newest committed request, focus and the live set. It derives `resolving` whenever the committed request names another project than focus's request, including before focus hears its first request. The comparison is by project, never by id or chat (`no-route-in-selector`, `match-by-request-id`).
2. **The same project is not a move.** A request for the project focus is on or moving to keeps focus's state. When focused, focus sends at most one `ChatForwarded`, and no leave flush, access question or session-creating open.
3. **Another project starts a move.** The session focus was on becomes the one being left. A leave flush still running for it is kept, so one flush is in flight; a failed one is not reused.
4. **Access is fenced.** Focus asks access once per request id, and again when the library epoch moved since its answer. It takes only an answer for its current request id (`no-request-id`). It starts the import beside the question.
5. **Answers.** A held answer gives `held`. A ready answer gives `opening` once the move's leave is done, else `leaving`, or `flushFailed` when the leave flush failed.
6. **A failed leave flush blocks.** `flushFailed` sends no open until `Retry`, which restarts the leave flush, or a newer request for another project. A library change does not retry it (programme control's ruling). Today it does, through the access effect's dependency on the library revision (`today-library-retry`); that coupling is accidental, and A5a changes the behaviour on purpose.
7. **The registry may close what is being left.** If the session being left closes while focus waits, its close flush stands in for the leave flush.
8. **Open.** `OpenAsked` happens only in `opening`, from a ready answer for the current epoch. It carries a request `{project, epoch}` built from that answer (`OpenCarriesRequest`). A failed start gives `held`.
9. **Withdraw a pending open that no longer stands.** When focus's open waits in `pendingOpen`, focus withdraws it (`cancelPendingOpen`) in the step it moves to another project, takes a held answer, or re-asks access after a library change, and sends it again only from the fresh answer. The re-ask also withdraws any other open of focus's waiting with a request from an older epoch. Kept requests need no step: as rule 13 says, any library change makes every kept request unusable. If the registry replies that it dropped focus's waiting open (stale under A5c), focus clears its open and sends it again from its fresh answer. When another open displaces it from the single slot, the registry sends no reply. Focus derives the displacement itself, because focus sends the displacing person's open, and does the same. Every outcome of another open displaces the slot: a wait takes it, and a spawn or a failed start into the room clears it (`sessions.machine.ts`, the `hasRoom` branch). A held answer also withdraws a person's open waiting for that project, since it drops the kept request. `OpeningWaitsOrWentLive` checks that every displacement is answered.
10. **Join four facts.** `opening` becomes `focused` only when access is ready for the current epoch, the import is loaded, the session is live in answer to focus's open (not waiting in `pendingOpen`), and its chat session and first file check are each settled or the open bound has passed. The move ends at the join.
11. **A session closed before the join.** If the session focus opened went live and then left the live set before the join, through a person's close or a budget close (idle expiry spares it), focus settles on the project as `focused`, which derives `closed` with the reopen offer. It neither reopens nor closes on its own. An open that never went live is not a close: rule 9's reply sends focus back to `OpenAsked`. That covers an open dropped as stale, and one displaced from `pendingOpen` by another open's wait, spawn or failed start into the room.
12. **Focus never closes.** Only `PersonClosed`, `PersonDiscarded`, `IdleExpired` and `BudgetSwitchClose` close a session (`FocusNeverCloses`). On a one-project device the registry's budget close takes the session being left, through that session's own close flush. If that close flush fails, the session is retained, live with its unsaved work (`CloseFlushFailed`). The open waiting in `pendingOpen` keeps waiting, unless it is for the retained session itself, which the registry then reopens (`reopenRetained`), so the waiting open goes live. It stays retained until a later close's flush succeeds or the person discards explicitly (`PersonDiscarded`, `DirtyNeverDiscarded`).
13. **A person's open goes through focus.** It carries the request focus kept for that project and does not move focus. A reopen of the focused project joins its facts again. A kept request records the epoch of its ready answer and is usable only at that epoch, so a library change drops every kept request in any state, `idle`, `flushFailed` and Home included. A held answer drops it at once.

## Inherited risk: the resume window, a requirement on A5c

The registry as built resumes a `pendingOpen` without looking at the library. Until focus withdraws its open, it can therefore spawn that open on a stale epoch (`target-resume-window`). For a route open, the window runs from `LibraryChanged` to focus's re-ask. For a person's open while focus is `idle` or `flushFailed`, focus does not re-ask, so the window is unbounded until A5c. Programme control accepted the witness and made closing the window a requirement on **A5c**. The open request carries focus's library epoch. The registry drops a resumed `pendingOpen` whose epoch is stale and **replies to focus that it dropped it** (`PendingOpenDropped`), so focus clears its open and re-sends from its fresh answer. `RegistryChecksEpoch = TRUE` models that registry, with the reply in the same step as the drop. `target-registry-epoch` is A5c's conformance target: `StaleResumeUnreached` and `NoSpuriousClosed` hold there with every target safety property. `liveness-registry-epoch` shows focus still settles; without the reply it does not.

## Risk for A5a: one leave flush in flight across a return

When focus returns to the project being left while that project's leave flush is still running, the model resets its record of the flush. The running flush's result is then ignored, and if focus leaves that project again it starts a new leave flush. The model keeps only one flush (`f.lf`), so it cannot show two in flight, and no property catches this. A5a must keep the running flush across a return, or wait for it before starting another flush of the same session, so that rule 3's "one flush in flight" holds in the machine.

## Sharpened statements (ruled)

Programme control ruled on these five statements. A5a implements them as written.

1. **`SameProjectKeepsEditor`.** The watch starts on a commit for the shown project while no library change is pending. It ends at a library change, a commit for another project, or the session closing.
2. **`FocusFollowsLatestRequest`.** "A newer request is still being resolved" means a committed request that focus has not heard yet.
3. **The target selector.** It derives `resolving` for an idle focus.
4. **`OpenOnlyOnCurrentAccess`.** It compares by project and by the current library epoch. An earlier ready answer for the same project counts only if no library change has happened since that answer was given (D7).
5. **A person's open in `flushFailed`, and a failing close flush (to A5a and A5c).** "A person's open is allowed while focus is in flushFailed, as D7 says. But if it makes the registry close the dirty session on a budget-1 device, and that close's own flush also fails, the session is not discarded. It stays retained, with its unflushed work, until a flush succeeds or the person discards explicitly (I6)." The model holds this in `target-retained-session` (`DirtyNeverDiscarded`), and `target-retained-session-reachable` shows the case is reached. The registry's budget cannot then admit the person's open, so it waits in `pendingOpen`.

## Other property statements

- `OpenOnlyOnCurrentAccess` also holds every open focus sends, a person's included, to a request for a project the library holds ready at its current epoch. It covers the registry's resume of a request focus sent: `SessionClosed` may spawn it only while focus still stands behind it (still opening that project from that answer, or keeping that request). It covers today's `Retry` run as well.
- `FailedFlushBlocks` has an action form, `FailedFlushSendsNoOpen`, in every passing config: while a failed leave flush blocks, no step of focus opens a session or fills `pendingOpen`. A person's open is allowed, because it is the person's command through focus and focus does not move (packages.md: `flushFailed` "does not move").
- `DirtyNeverDiscarded` (I6, ruled): a dirty session never leaves the live set in a step where its close flush failed, and unsaved work leaves the dirty set only by a successful leave or close flush or the person's discard. It is in every passing safety config and gives `CloseAfterFlush` a failing close to rule out.
- `OpeningWaitsOrWentLive`: while focus has an open out that has not gone live, it is still waiting in `pendingOpen`, so every displacement got its reply. With the replies in place, `TOpenLost`'s `f.live` guard is implied by this invariant, so deleting the guard alone changes no reachable behaviour and no config catches it. The invariant pins the replies instead.
- `NoSpuriousClosed` (in `target-registry-epoch`, which has no person close): focus is never `focused` with a fresh ready answer on a project whose session is gone and not waiting.
- `FlushBeforeLeave` is stated over the dirty set, which the person and the flushes own: while focus is `opening` or `focused` on a project, no other project holds unsaved work. It no longer reads focus's own record of the move.
- `OpenCarriesRequest` checks each live session's request, and `pendingOpen`'s, against the library's own history: the project was ready at the epoch the request names.
- `EditorJoinFresh`: focus enters `focused` with the editor shown only from a ready answer for the library's current epoch.
- `EditorOnlyWhenReady` states its fact condition directly (chat session and first file check settled, or the open bound passed), not through the join's guard.
- `EditorOnlyForCommittedProject` holds the selector to `resolving` before any request is heard, which covers the server render and the first client render.

## Abstracted away

- The unload sequencer (D26). Its order is one pass with nothing to interleave, so test rows in A0.2, A5b and A7c hold it.
- What a flush writes, why a region fails, and slug resolution: a request already names its project or `Home`.
- What a chat is. It is one opaque value in the request; the model checks only that changing it never moves focus.
- The length of the open bound and of the idle window. Both are steps that may happen.
- The held answer's kinds, `Touch`, the registry's recency order, and today's retained kernel (`project-route.tsx` 211 to 219).
- The registry's answer to a refused budget close. The model's `BudgetSwitchClose` closes a retained session again under fairness, while the built registry emits `budgetRefused` and waits for the person. Liveness does not depend on that difference.
- The registry's internals. Its steps (the single `pendingOpen` slot, the budget-1 close, idle expiry) are pinned by A0.2's rows against `sessions.machine` as it is.

## Drift

`project-focus.drift.test.ts` hashes `ProjectFocus.tla`, every config and `expected.json`, and today's route code: `project-route.tsx`, `project-route-state.ts` and `project-live-sessions.tsx`. `sessions.machine.ts` is left out because the registry is environment here.
