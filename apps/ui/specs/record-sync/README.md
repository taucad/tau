# Record sync: own-write attribution

`RecordSync.tla` models one record store and its file. It checks how the store attributes the bytes it reads back: as its own write, or as another party's. It is the spec for the `recordSync` machine of the graphics event-driven state charter (D6, D12, invariants I5 and I12) and it lands before that machine, under formal verification policy rule 1.

The entries store (`entries-store.ts`) implements this protocol today with slots compared inside a race window; `view-store.ts` did too until G1 (at `dd5ea47e`) and the layout store (`workbench-layout-controller.ts`) until G2b (at `0dbd19d9`), and both are now shims over `recordSync`. Every `view-store.ts` line cited below is at `dd5ea47e`, and every `workbench-layout-controller.ts` line at `0dbd19d9`. The model holds their attribution as switches beside the target, so the same properties are checked against what is built and against what `recordSync` will do.

## Parties and abstraction

| Party   | Model                                                                                                                                                                                                                                                                      |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writer  | One checked write at a time, expecting the bytes the store last published                                                                                                                                                                                                  |
| File    | The authority applies a checked write only while the file still holds the expected bytes. `file.ver` and `file.author` are ghost variables                                                                                                                                 |
| Watch   | Every change emits a change event. An event is delivered after any delay and any number of times (`watch`, `echoes`)                                                                                                                                                       |
| Reads   | Started by a change event, by a conflict, by the person's retry (`ForcedRead`, bounded by `MaxForced`), as the refresh of an overlapped write, or, in the slot modes, as the read-back of a write whose reply was lost (`Resolve`). Only the latest read reaches the store |
| Foreign | Another writer of the same file. Its bytes may equal bytes this store wrote                                                                                                                                                                                                |

The model is untimed. The edit debounce, the retry backoff and a flush are the one step `IssueWrite`, and a change event that is never delivered is an event delayed forever. Bytes are opaque values and a digest is its bytes, so the model assumes no hash collision. A write's bytes are any bytes other than the published ones: the model does not derive them from a patch.

A write whose reply is lost (`LoseReply`, bounded by `MaxLost`) may have been applied, may be applied at any later step, or may never be applied. That is the `potentially-applied` state the filesystem bridge reports for a dropped connection or an abort after sending. The fairness of `LiveSpec` keeps it that way: it makes the authority decide a write whose reply is pending, not one whose reply was lost, and makes the watch deliver a pending change event, not deliver one again.

## Properties

| Property                | Kind      | Meaning                                                                                                           |
| ----------------------- | --------- | ----------------------------------------------------------------------------------------------------------------- |
| `OwnWriteAttributed`    | invariant | I5. A snapshot that shows a version this store wrote has `origin` own                                             |
| `ForeignStaysForeign`   | invariant | I12. A version another party wrote has `origin` own only when its bytes are identical to an outstanding own write |
| `SnapshotMonotone`      | action    | The snapshot never steps back to an older version of the file                                                     |
| `FenceStopsWrites`      | action    | Once the view is fenced the store issues no write                                                                 |
| `EditEventuallySettled` | liveness  | Every edit is written or the view closes. Quiescence predicate: `Settled`                                         |
| `EventuallyCurrent`     | liveness  | Once writes stop, the snapshot shows the bytes the file holds. Quiescence predicate: `Current`                    |

The liveness pass is a bounded claim. `liveness-flush` passes at five writes, which is as many as two edits, one foreign write and one lost reply need. The same configuration violates `EditEventuallySettled` at four writes, and at five writes with a second foreign write, both times because `MaxWrites` is spent while an edit is still unwritten, not because the protocol is stuck. Those two runs were made for this review and no committed configuration records them. A liveness failure after a bound is widened is therefore first a bound artefact. The model makes no claim about unbounded retries.

An own write is **outstanding** while its reply is pending or lost. An acknowledged write stays outstanding until the store reads other bytes in a read that started after the acknowledgement, or acknowledges a later write. This is the store's knowledge, not the file's truth: the store cannot tell a foreign write of identical bytes from its own echo before it has seen the file move on. The ghost variable `superseded` records it independently of the map the store keeps (`kept`).

A lost write stays outstanding for good, and that is a limit of the model. No modelled rule ends the entry of a write whose reply was lost, so the model excuses a foreign write of a lost write's bytes without bound: `ForeignStaysForeign` holds for lost writes by definition, not because the store learns anything. The record-sync blueprint as written also drops such an entry at the first read attributed foreign that started after the write was issued (own-write identity rule 3, which `issued-before-read` models). Once target rule 3 replaces the blueprint's "drops every entry older than the read's start", the own-write time to live of `recordSync` (own-write identity rule 4) is the only thing left that ends such an entry, and expiring it reopens I5 for a lost write that lands later. The as-built stores have no time to live: they forget a lost write at its read-back, which the slot modes model.

## Target rules

These are the rules the `target` configurations check. `recordSync` implements them. Rules 1, 3, 4, 5, 6 and 7 have witnesses that fail without them, and `no-digest` removes the map that rule 2 looks up. Rule 6 guards no safety property: with `WaitLatestRead = FALSE` at the scope of `target`, which has no lost reply, the safety properties pass. That run was made for this review and no committed configuration records it. Rule 6 keeps the writer from spending attempts on a base it already knows is stale, and its witness `no-wait-latest-read` violates `EditEventuallySettled` at three writes, a scope at which the target passes.

1. Every write adds an entry to the map when it is issued. Entries are per write and never merged by digest: two writes of the same bytes hold two entries, and a conflict reply removes only its own write's entry. A lost reply keeps the entry. Witness: `digest-keyed-entries` (a write lands and its reply is lost, the retry of the same bytes conflicts, and removing every entry with those bytes leaves the conflict read to publish the store's own bytes as foreign).
2. A read is attributed own when its bytes match an entry, in any state.
3. A completed read drops every acknowledged entry whose bytes differ from the bytes it read, whether the read was attributed own or foreign. It never drops an entry whose reply is pending or lost. Witnesses: `issued-before-read` (dropping entries by issue time loses the echo of a write in flight), `drop-on-foreign-only` and `foreign-identical-bytes`.
4. An acknowledged write drops the earlier acknowledged entries. Witness: `keep-earlier-acknowledged`.
5. A read overlaps a write when it starts or completes while the write is in flight. The reply of a write that no read overlapped publishes the write as own and supersedes any read still in flight. The reply of an overlapped write publishes nothing and starts a refresh read, which the map attributes. Witnesses: `publish-on-overlap`, `no-refresh` and `overlap-on-start-only` (a read that started before the write was issued and completes while it is in flight publishes a newer foreign version, and the reply then publishes the older own version over it).
6. After a conflict or an overlapped reply the writer waits for the latest read, including a watch or forced read that superseded the one its reply started. Witness: `no-wait-latest-read` (a watch read supersedes the refresh or conflict read the writer waits for, the writer issues its next write on the base it already knows is stale, and that write conflicts with the write bound then spent, so the second edit is never written).
7. The close fence stops new writes. Witness: `no-fence`.

Rule 1 refines the blueprint's `ownWrites`, a map keyed by digest: the map is looked up by digest, but its entries belong to writes. Rules 3 and 4 refine the blueprint's "drops every entry older than the read's start". Rule 5 refines "published once as `origin:'own'`" for the overlapped case. With rule 5, every read that completes started after the last acknowledgement, which is why rule 3 needs no timestamps. The spec contradicts the blueprint's own-write identity rule 4, which calls the own-write time to live "a leak guard only. Correctness never depends on it." With rule 3 in place the time to live is the only thing left that ends the entry of a write whose reply was lost, and expiring that entry reopens I5 if the write lands later, so G1 must not treat the time to live as correctness-neutral for lost writes.

### How `recordSync` schedules the writer

The target lets the writer issue its next write at any step. `recordSync` is one scheduler among those, and `EagerWriter = TRUE` is that scheduler, so the covering suite the machine replays contains only behaviours the machine can take:

- **The writer continues in the task of the read it waited for.** When a conflict read or a read-back completes, the machine issues the next write, or finds nothing left to write, in the same step. The model takes `CompleteRead` and then `IssueWrite` or `Forget`, with `readBack` set between them so that only the authority and other writers can move.
- **A lost reply is read back before the next write.** After `LoseReply` the writer writes again only once a read that started after the loss has completed (`owed`). A change event's read is that read-back when it starts in time (`rd.back`); otherwise the writer starts one (`Resolve`) when its retry timer fires or a flush asks. The target's safety properties do not need the read-back: it saves a write that would only conflict, as the stores did before.
- **Nothing left to write.** When the bytes the writer waited for already hold the person's change, the merged record serializes to the record shown and no write is issued (`Forget`). The entry of a lost write stays (rule 3).

`target-eager` checks the safety properties and `liveness-eager` the liveness properties under this scheduler. The machine keeps the entry of a lost write for good, as rule 3 says, with one bound the model does not have: it keeps at most eight lost entries (`maxLostWrites`) and drops the oldest past that. It has no time to live. A lost write that lands after eight later lost replies would read as foreign.

## What the as-built configurations show

- **`today-slots`** is the incident's counterexample. A change event starts a read while the write is in flight. The reply sees that read and starts a refresh read. A second change event starts a read after the reply, which supersedes the refresh. The in-flight set is empty by then, so the store publishes its own bytes as a foreign read. The entries store still does this, and the layout store did until G2b; G2 moves both onto `recordSync`.
- **`post-1602-slots`** answers handoff review R17 for a reliable reply channel, no forced read and one write at a time: the acknowledged slot closes the race at this scope. The pass rests on `publish` returning early for bytes already shown, which a forced read skips (`post-1602-forced-read`).
- **`post-1602-lost-reply`**: the store forgets a write whose reply was lost as soon as the read-back returns, also when a watch read superseded that read-back. The read-back does not protect the write in either case: a watch read supersedes it, or it returns the old bytes before the lost write lands; the store forgets the write all the same. When the lost write has landed, or lands later, no slot holds it. A read that returns its bytes then publishes the store's own bytes as foreign. Among the counterexamples the model finds: a later read while a write of other bytes is in flight (the retry has other bytes only when an edit arrived in between); the conflict read of a retry of the same bytes, issued before any read has published the landed bytes; and a read after the writer found nothing left to write (`Forget`). As built, nothing is left to write when an edit reverts the pending patch: the merged record serializes to the shown record, and `write` returns `'saved'` right after `unresolved = undefined`.
- **`post-1602-forced-read`** (R17): `retryRead()` calls `read(true)`, and the first successful read after a failed one passes `recovered`; either way `publish` runs although the bytes are the ones already shown. After the reply of a write that no read overlapped publishes it as own, no slot holds the write any more, so a forced read of the same bytes publishes them as foreign. The entries store has the same forced path, and the layout store had it until G2b. The model's `ForcedRead` stands for both kinds of forced read; read failures themselves are not modelled.
- **`post-1602-ForeignStaysForeign`** needs one foreign write. A read overlaps the first write; its reply sets the acknowledged slot and starts a refresh read, which a change event supersedes, so the slot stays. No read overlaps the second write, and its reply publishes it without clearing the slot. A foreign write of the first write's bytes is then read as the store's own. With the same single foreign write the model also finds the slot surviving a read matched to the write in flight. Both are recorded because the model finds them, not because they are likely.
- **`post-1602-SnapshotMonotone`**: a read that started before the write was issued is not an overlap as built, so it can publish a newer foreign version and the reply then publishes the older own version over it. The next change event corrects the snapshot.

The four `post-1602-*` defects name G1 as their fix. The as-built side of every finding here comes from reading the code of the three stores, not from a browser reproduction, so under R17 they are no reason for a change outside G1.

## Correspondence to implementation

### The stores as built

Names are from `apps/ui/app/workbench-records/view-store.ts` as it was before G1 made it a shim over `recordSync` (`git show dd5ea47e:apps/ui/app/workbench-records/view-store.ts`). The entries store has the same shape without the acknowledged slot. So did the layout store before G2b (at `0dbd19d9`), except that its `publish` awaited a digest and published nothing if the read generation changed meanwhile, which is not modelled (see Not modelled).

| Model                           | Runtime seam                                                                                                                                                                           |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IssueWrite`, `wr[w].expected`  | `write` → `writeFileChecked` with `preconditions: [{ path, expected }]`; `inFlightWriteBytes.add`                                                                                      |
| `FsDecide`                      | The authority's checked precondition on the file's bytes                                                                                                                               |
| `ReplyApplied`, `overlap`       | `generation === generationAtWrite` publishes `'write'`; otherwise `acknowledged` is set (view store) and a refresh read runs                                                           |
| `ReplyConflict`                 | `result.status === 'conflict'` → `read()`, then the next attempt                                                                                                                       |
| `LoseReply`, `Lost`             | `isPotentiallyApplied(error)` → `unresolved = attempted`                                                                                                                               |
| `Resolve`, `readBack`, `Forget` | `(!observed \|\| unresolved) && !(await read())`, then `unresolved = undefined` in the same task                                                                                       |
| `WatchRead`                     | `watchRecordFile` → `store.read()`; `++generation` supersedes the read in flight                                                                                                       |
| `ForcedRead`, `rd.forced`       | `retryRead()` → `read(true)`; also the first successful read after a failed one (`recovered`)                                                                                          |
| `ServeLater`                    | `exists` and `readFile` answered at any point before the read returns                                                                                                                  |
| `CompleteRead`, `kept`          | `current === generation`, the lookup over `inFlightWriteBytes`, `unresolved` and `acknowledged`, then `publish`                                                                        |
| `Unchanged`                     | `publish` returns early when `sameBytes(state.bytes, bytes)` and not `notify`                                                                                                          |
| `CloseFence`                    | `fenceClosedView`, `dispose`, `closed()`. The target publishes nothing after the close; as built, a write reply that arrives after it still publishes, which the model does not follow |
| `st.origin`                     | `onChange(state, source, locallyAuthored)`: `'write'` is own, `'read'` is foreign                                                                                                      |

In the slot modes a read that returns the bytes already shown publishes nothing, as built, unless it is forced: `retryRead()` and the first successful read after a failed one publish anyway (`notify || recovered`). In the target every completed read is attributed, so the target properties do not rest on that early return.

### `recordSync`

Names are from `apps/ui/app/workbench-records/record-sync.machine.ts`. Each transition names its action in `meta.tla`; `RecordSync/drift.json` lists them.

| Model                            | Machine                                                                                                                                                              |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Edit`, `dirty`                  | `edit` in `intent`: the patch joins `pending`. `dirty` is `pending`, `deferred` with no write carrying it, or a cycle waiting for its base                           |
| `IssueWrite`, `wr[w].expected`   | `write.starting`: the debounce or retry timer, a flush, or the read the writer waited for. `expected` is `published.bytes`; the entry joins `ownWrites` in this step |
| `Resolve`, `owed`, `rd.back`     | `write.starting` with `readBack: 'owed'` raises `write.readRequested`; `readBack` is `'reading'` once a read that started after the loss is in flight                |
| `Forget`                         | `write.starting` ends the cycle as saved when the merged record serializes to the record shown                                                                       |
| `ReplyApplied`, `overlap`        | `write.writing` `onDone`, `applied`: publishes own and raises `write.published`, or enters `awaitingRefresh` and raises `write.readRequested`                        |
| `ReplyConflict`                  | `write.writing` `onDone`, `conflict`: removes the write's entry, enters `awaitingBase` and raises `write.readRequested`                                              |
| `LoseReply`                      | `write.writing` `onDone`, `failed` with `lost`: the entry's state becomes `lost` and `readBack` becomes `'owed'`                                                     |
| `WatchRead`, `ForcedRead`        | `read` and `retryRead` in `source`: re-enter `reading`, which supersedes the read in flight; its waiters wait for the latest                                         |
| `CompleteRead`, `kept`           | `source.reading` `onDone`: the lookup over `ownWrites`, the drop of acknowledged entries with other bytes, `published`                                               |
| `readBack`                       | No state: the writer's `source.completed` step runs in the macrostep of the read's `onDone`                                                                          |
| `CloseFence`                     | `close`: `source` and `intent` become final; `write` becomes final at once or when the write on the wire answers, and nothing is published after the close           |
| `FsDecide`, `ServeLater`, `file` | The `checkedWrite` and `readRecord` ports of the composition root (`record-sync.ts`)                                                                                 |
| `st.origin`                      | `origin` in context and on the `published` event                                                                                                                     |

A read that returns the bytes already shown updates `origin` and emits no `published` event unless it is forced or follows a failed read. The model publishes on every completed read; the two agree on `st`.

## Not modelled

- Refusals (`INVALID_RECORD`, `NEWER_RECORD`), `ensure`, `reset`, `restore` and health reporting. They do not take part in attribution. `restore` (added by G2b for the layout record's _Restore previous arrangement_) is one checked write of a saved record on the exact bytes the person reviewed: refused while anything is owed, waiting or being written, never rebased after a conflict and never retried after a failure. Unsaved, it ends on the record shown as the base of the person's next diff: its conflict read's, or, when its reply was lost, the record shown before it. Its own-write entry is marked `restored`, so a later read that finds a lost restore landed, once nothing is owed, settles the base on the restored record although the read is the store's own. Its write goes through the one `write` region and records its own-write entry by its exact bytes like any checked write, so the attribution rules hold for it unchanged; like `reset`, its transition is labelled `Unmodelled`.
- Read failures. A failure takes part only through the read after it, which publishes like a forced read (`recovered`); `ForcedRead` stands for it.
- The patch algebra (`diff`, `combine`, `merge`). The record-sync blueprint covers it with property tests. So is the policy's optional `keepsBaseOnAbsence` (set by `layoutPolicy`): while the shown record is absent it keeps the last record a publication showed (the one the host keeps showing) as the base of the person's next diff instead of clearing it. The machine applies it through one helper wherever it sets `intended` from the record shown: a foreign read in `CompleteRead`, a saved edit, reset or restore cycle in `settle`, and every restore that ended unsaved. The model's file is never absent and the model has no diff base, so neither update of `intended` has a counterpart in the spec and the refinement mapping does not compare it; the layout conformance replay says so.
- A `known-not-applied` write failure. Nothing reached the authority, so it is a write that was never issued.
- The own-write time to live of the blueprint's `recordSync` (own-write identity rule 4). Once target rule 3 replaces the blueprint's "drops every entry older than the read's start", it is the only thing left that ends the entry of a lost write. The as-built stores have none, and the model has no rule that does, so the model excuses a foreign write of a lost write's bytes without bound. Expiring an entry reopens I5 for a lost write that lands later. See the paragraph on outstanding writes. `recordSync` as G1 built it has no time to live either; its bound on the number of lost entries (`maxLostWrites`) is not modelled.
- The writer's other reasons to end without a write. In `recordSync` an edit that changes no field, or one that merges to the record shown, ends with nothing written at any time; the model has that step only after a read the writer waited for (`Forget`). Three conflicts in a row end the edit as failed and a timer retries it; the model's bound is `MaxWrites`.
- A write reply after the close. `recordSync` lets the write on the wire answer its requester and publishes nothing; the model stops following replies at `CloseFence`.
- A second write in flight. The model's writer issues one checked write at a time. As built, `flush()` awaits `pending` and then calls `write()` without chaining that call onto `pending` (`view-store.ts:647` at `dd5ea47e`, `entries-store.ts:540` and `:554`, `workbench-layout-controller.ts:517` at `0dbd19d9`), while an edit's write is queued on `pending` (`queueWrite`), so an edit that arrives during the flush write puts a second checked write in flight. The `post-1602-slots` pass therefore also assumes one write at a time. Reasoning from the code, not a model result, with replies in apply order: in the three-slot view store the flush write of `b`, expecting `a`, is applied and a watch read publishes `b` as own, matched to the write in flight; an edit's write of `c`, expecting `b`, goes in flight beside it and is applied; the reply for `b` arrives first, finds the read generation changed, sets the acknowledged slot to `b` and starts a refresh read (`view-store.ts:464-467` at `dd5ea47e`), which reads `c`, compares it with `b` only and not with the writes in flight (`:469`), and publishes `c` as foreign (`:471`); the reply for `c` then refreshes and reads `c`, and its publish returns early because those bytes are already shown, so the snapshot stays attributed foreign. That is an I5 violation with no lost reply, no forced read and no reordered reply. The record-sync blueprint's `write` region has one `writing` state that invokes one `checkedWrite`, so the target's one write at a time is the blueprint's rule, and G1 must keep it, `flush` included. G1 kept it: in `recordSync` a flush is a request the one writer serves.
- The layout store's asynchronous `publish`, before G2b. In `workbench-layout-controller.ts` at `0dbd19d9`, `publish` awaits a digest and then returns without publishing if the read generation changed meanwhile (`:144`, `:154-157`), so a read that starts during the digest drops the publish in progress, a write reply's included. The reply of a write that no read overlapped bumps the read generation and awaits `publish(…, 'write', …)` (`:304-306`), its in-flight entry already deleted (`:301`); a change event starts a read during the digest, the reply's publish is dropped, and the read finds no slot and publishes the store's own bytes as `'read'`. In `slots2` the reply publishes in one step. The view and entries stores publish synchronously (`view-store.ts:232` at `dd5ea47e`, `entries-store.ts:152`). Reasoning from the code, not a model result. It is not modelled because it only adds I5 counterexamples for a store that `today-slots` already records as violating I5. It opens no I12 path that this review found: every event that ends a write's outstanding state bumps the read generation. Since G2b the layout store is a shim over `recordSync`: the machine attributes and publishes in one step, and the shim shows each publication in that step, with a synchronous digest of its bytes, so neither attribution nor the person's diff base depends on a digest.
- `invalidateRead`. It is a read that never completes.
- The file's absence. A missing file is one more byte value.

## Bridge to the machine

- **Step label.** `act` names each step when `Labelled = TRUE`, which only `export` sets; elsewhere it is constant, so the checked configurations pay nothing for it.
- **Graph and suite.** `expected.json` has a `graphs` entry for `RecordSync` with `export` and the phase `rd.purpose`. `RecordSync/graph.json` is the reachable graph (6,865 states) and `RecordSync/suite.json` the covering suite: 42 behaviours, one shortest behaviour per read purpose and action.
- **Replay.** `apps/ui/app/workbench-records/record-sync.machine.conformance.test.ts` replays every behaviour of the suite on a live `recordSync` actor over a held file and compares the snapshot's origin and bytes, the read in flight, the entries kept, in flight and lost, `overlap`, `dirty`, `readBack`, `owed` and the phase after each step. The model's ghost variables and bounds are not compared.
- **Action names.** Every transition of the machine carries `meta.tla`, a model action or `Unmodelled`. The same test checks that each named action is an operator of this module and that every store action is named by a transition.
- **Drift.** `RecordSync/drift.json` holds the machine's alphabet, version and action names and this module's hash. A change to either side without the other fails the test.

Regenerate the graph, the suite and the manifest with `node tools/formal/src/cli.ts update apps/ui`.
