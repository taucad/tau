# Runtime Document Topology

## Current contract

The runtime hosts kernel plugins behind a document and view API. A client opens a source once, receives evaluations, subscribes to selected views, and exports from a document. The worker owns kernel selection, dependency resolution, caches, watches, native handles, and the serial native-operation lane. This page describes the current implementation; earlier command-driven proposals remain in the [source API blueprint](../research/runtime-source-api-unification-blueprint.md).

The public contract is defined by [`RuntimeClient`](../../packages/runtime/src/client/runtime-document-client-core.ts), [`RuntimeDocument` and `ViewSubscription`](../../packages/runtime/src/client/runtime-document.types.ts), and the checked [document protocol](../../packages/runtime/src/types/runtime-document-protocol.schemas.ts). Product-selected kernels are a host composition decision, not a property of the client protocol.

## Client and worker responsibilities

`createRuntimeClient({ transport, config?, operationTimeout? })` binds a transport. `connect()` initializes its worker and capabilities. `open({ source, parameters?, evaluateOptions?, stage?, watch?, signal? })` returns a document handle and starts its first evaluation; `evaluation()` awaits an outcome, and `update()` starts a new intent. Sources may be rooted filesystem entries or inline files. A document's `view(id?, request?)` returns a subscription whose `rendering()`, `update()`, `on('rendered', ...)`, and `close()` control one selected view. `document.export(target, request?)` writes from a selected native or transcoded export route. A document can have multiple views, and each view has its own request freshness. The document exposes `described`, `evaluated`, `progress`, and `status` events. The client exposes capabilities, state, log, telemetry, and connection errors.

Evaluation options belong to the document build. View options and content belong to a view request; export options and content belong to an export request. A committed evaluation pins its source revision for an export even if newer source is staged meanwhile. Native handles are an opportunistic cache: the worker can reheat a pinned evaluation from its source revision when the handle is absent. The client also provides one-shot `describe`, `snapshotSource`, and `transcode`, route inspection (`routesFor` and `bestRouteFor`), operation and transcode timeout setters, and `terminate`/`shutdown`. These methods do not recreate the retired `render`, `updateParameters`, `setOptions`, or client-wide `export` facade.

The trusted host gives the runtime an opaque, writable filesystem rooted at virtual `/`. Runtime paths and watches are local to that root; the worker does not receive the host's project ID, global route, authorization object, or authority-global file pool. The filesystem bridge enforces that boundary. A document with `watch: true` tracks its entry and resolved dependencies. The worker reconciles the union of active watch paths, rereads changed files through the rooted filesystem, invalidates relevant caches, and schedules affected document evaluations. An explicit document update carries its own intent and can stage source bytes; watched changes can also produce an evaluation without a new client command. Watch availability is an optimization: source freshness checks still apply when a filesystem cannot watch. See [`KernelWorker`](../../packages/runtime/src/framework/kernel-worker.ts) for the admission, watch, cache, and source-revision rules.

The worker serializes kernel/cache/watch/native state. A newer unpinned document intent supersedes an older evaluation; each view request and export operation has its own identity and terminal outcome. Kernel V2 hooks resolve and describe source, evaluate a native handle and offers, render a selected view, and write a selected export. Middleware and transcoders run around the appropriate operation. The worker checks request identity before publishing results, so late bytes or an aborted native call cannot become the current rendering.

## Transport and protocol

The runtime core uses [`RuntimeTransportClient` and `RuntimeTransportHost`](../../packages/runtime/src/transport/runtime-transport.types.ts). Bundled in-process, web-worker, node-worker, and Electron utility transports own their channels, filesystem bridge, shared-memory allocation, binary delivery, and timeout recovery. The client core does not access `MessagePort`, `SharedArrayBuffer`, or transfer lists directly. The [document dispatcher](../../packages/runtime/src/transport/_internal/runtime-document-dispatcher.ts) receives a transport-supplied generic RPC `Port`, passes the supplied signal buffer to the worker, and forwards transfer lists for binary results; it does not allocate the shared buffers. A transport initializes the host with its memory handle and resolves binary content for the client. When an isolated host does not acknowledge cancellation before its recovery deadline, the transport can terminate it; a same-isolate transport cannot enforce a wall-clock deadline while synchronous work blocks its event loop.

The v4 document wire has six acknowledged calls: `initialize`, `describe`, `export`, `snapshotSource`, `transcode`, and `dispose`. Client notifications are `open`, `update`, `close`, `openView`, `updateView`, `closeView`, `abort`, and `binaryMaterialised`. Worker notifications are `described`, `evaluating`, `evaluated`, `rendering`, `rendered`, `progress`, `errorEvent`, `stateChanged`, `log`, `logBatch`, `telemetry`, and `capabilitiesUpdated`. The [protocol name inventory](../../packages/runtime/src/types/runtime-document-protocol.types.ts) and schemas are the authority for exact payloads. Worker-to-client progress and results use the ordered RPC channel; no SAB state monitor supplies a second event stream.

The transport can deliver render and export bytes inline, by transfer, or through an optional `SharedPool` geometry buffer. The client materializes bytes before exposing a rendering or export result and acknowledges pooled frames with `binaryMaterialised`; stale frames are acknowledged too. The rooted filesystem bridge and its shared-memory configuration are separate from this binary delivery pool. If a pool cannot be allocated, delivery falls back to a non-pooled tier. See [`sab-pools.ts`](../../packages/runtime/src/transport/_internal/sab-pools.ts) and the [document materializer](../../packages/runtime/src/transport/_internal/document-materialiser.ts).

## Native cancellation

The transport's cooperative-abort signal is one **8-byte `BigInt64` word at byte offset 0** (`signalBufferByteLength = signalBufferMaxByteLength = 8`). It packs a 32-bit native-operation sequence, a 30-bit generation, and a two-bit reason. The worker publishes a new sequence/generation only when its native operation enters the serial lane and invalidates that state when the operation leaves. The client transport uses an atomic compare-and-swap against the exact sequence and optional generation, accepting only the first reason. A stale document, view, or export cannot abort a successor. The [state encoding](../../packages/runtime/src/framework/document-abort-state.ts), [transport signal helper](../../packages/runtime/src/transport/_internal/abort-channel.ts), and [cooperative check](../../packages/runtime/src/framework/cooperative-abort.ts) define this contract.

Synchronous native work cannot receive an ordinary worker message until it yields. OpenCascade and Replicad call `checkAbort()` through the OCCT wrappers before native calls; PicoVoxel checks before its facade calls. A changed atomic word invokes the active operation's abort callback with the published reason and throws the internal `RenderAbortedError`. Async operations also receive an `AbortSignal` and an ordered `abort` notification. PicoGK sends its signal to a separate native-process session, whose build request uses a cooperative `cancel` method. The worker arms distinct atomic tokens for native evaluation, view render, and export write; request identity and terminal checks still guard publication when one native call cannot be interrupted immediately. The [document abort tests](../../packages/runtime/src/framework/document-abort-state.test.ts) cover reason ordering, stale tokens, and sequence isolation; [V2 worker tests](../../packages/runtime/src/framework/kernel-runtime-worker.v2.test.ts) cover document and native-hook integration.

If `SharedArrayBuffer` is unavailable, the transport omits the signal word. Ordered abort messages and operation signals still work when the worker can process them; an isolated transport's timeout recovery bounds a native call that does not yield. This is the same degradation path as binary delivery without a pool.

## Historical boundary

The older autonomous-preview proposal used `openFile`, `updateParameters`, `setOptions`, `geometryComputed`, a two-`Int32` abort slot layout, and a client-wide render outcome. Those commands and callbacks were retired with the document/view protocol. Its motivation remains: dependency watching and native cancellation belong beside the worker's caches and kernel state, while the host chooses which documents and views to display. The [rooted-filesystem investigation](../research/runtime-model-load-project-root-regression-v3.md) records the authority boundary that the current topology preserves.
