# Workspace Filesystem and Revisions

## Status

**Current** (2026-09-20) — the implemented architecture for how files, revisions, branches, and agent working copies relate across every Tau host (browser, desktop, `tau serve`, CLI, cloud). It is the filesystem-and-revisions half of the workspace-anchored topology ruled in [docs/research/client-host-topology-and-filesystem-authority.md](../research/client-host-topology-and-filesystem-authority.md) (rulings N1–N36) and refines, without contradicting, [docs/policy/filesystem-authority-policy.md](../policy/filesystem-authority-policy.md) and [docs/policy/filesystem-policy.md](../policy/filesystem-policy.md). The execution history is [docs/research/workspace-filesystem-north-star-blueprint.md](../research/workspace-filesystem-north-star-blueprint.md); the file-tree presentation slice is [docs/research/file-tree-mount-provenance-blueprint.md](../research/file-tree-mount-provenance-blueprint.md).

The local implementation and regression matrix are complete. Credentialed GitHub, clean-machine packaged desktop, production R2, and Fly recovery validation remain external operator gates; they do not weaken the local contracts below.

The Tau Hosted Remote's storage substrate was re-ruled on 2026-09-18 by the [git storage substrate charter](../research/git-storage-substrate-charter.md): object storage is authoritative, the Fly volume is retired, the browser repository is `.git`, and a project may have collaborators. The passages below carry that ruling. The charter's own deployment gate (a second copy, regional measurements, a staging proof and the production apply) is still open, so **Tau Cloud sync is not open to users yet**; the server-side contract is [revisions cloud architecture](revisions-cloud-handbook.md), and operating the deployed system is covered by the private operations handbook. Normative rules are extracted into `docs/policy` (topology OQ-N20).

## Why this document exists

Tau's promise is that **the filesystem is the API** ([vision-policy](../policy/vision-policy.md): "Everything is a file… history stay[s] portable and runnable outside Tau"). Files, revisions, and agent working copies were each built well in isolation, but they are presented through three parallel projections — the Files tree reads the authority, the agent reads a composed rooted view with overlays and masks, and revision cards are derived from chat transcripts — and the word "workspace" carries fifteen meanings across the corpus. The visible symptoms: a chat that appears to work in a different filesystem from the Files pane, `run_*` directories that look like project folders, skill links that open "File not found", two panes each claiming "Current", and a Revisions pane whose numbers come from the transcript rather than from stored history.

This document names one canonical representation and derives every surface from it.

## The one sentence

> Every consumer — agent tool, Files tree, editor, viewer, parameters, revisions pane, export, CLI — reads **one composed view of one checkout**. A **checkout** is a working copy of a **project** that tracks a **branch** of that project's **revision graph**. Revisions are the only durable history; checkouts are working state; everything else is a projection.

The rest of the document is the elaboration of that sentence.

## Layers

```text
L5  Porcelain        Files · Editor · Viewer · Parameters · Revisions pane · Chat links · Composer picker · CLI verbs · agent `revisions` tool
                     ─────────────────────────────── one checkout selection per workbench ──────────────────────────
L4  Composed view    composeView(checkout, overlays, mask) → RootedFileSystem + provenance per entry   (all hosts)
L3  Checkouts        live checkout (project dir)  ·  linked checkouts (<workspace>/.tau/checkouts/<project>/<id>)  ·  leases
L2  Revisions        one repository per project · BACKEND (RevisionPort) · branches · change ids · evidence/chat refs
                     REMOTES: git smart HTTP + LFS only · Git remotes · Tau Hosted Remote (git server in Tau API) · atomic receive
L1  Authority        WorkspaceFileService (composition root) · mount table · rooted views · mutation pipeline
                     tree indexes · project routes/directories · external-change ingest · watch planes
                     PATH REGISTRY (one classifier), injected as a PathPolicy — never imported by the core
L0  Storage roots    DirectIdb · OPFS · WebAccess · Memory · Node fs
```

### L0 — Storage roots _(holds today)_

Unchanged. One provider per storage root; mounts route; no overlay provider exists and none is introduced (the mount-only ruling stands). The composed view (L4) is built _above_ the authority, not as a provider.

### L1 — Authority and the path registry

The authority exposes one function that every other layer consults:

```ts
classify(path: string): {
  class: 'authored' | 'records' | 'cache' | 'control-plane';   // Rule 16 storage class
  versioned: boolean;                                          // enters a revision
  agentAccess: 'read-write' | 'read-only' | 'hidden';          // composed-view mask
  watch: 'ui' | 'kernel' | 'none';                             // which watch plane
}
```

`path-registry.ts` owns the `PathRegistry` rows and `tauPathPolicy`. Every row is normalized to NFC, lower-cased, stripped of trailing dots and spaces, and stripped of a segment's `:` suffix before matching. Root rows match only the root; control-plane rows match segments at any depth. On a case-sensitive disk, `Exports` is therefore Tau's reserved `exports`; Win32 8.3 short names are outside the contract.

The registry is structural, not a glob: it is keyed by the project's reserved `.tau/**` layout (below), by the mount table (dependencies), and by the checkout kind (a linked checkout classifies its own `.tau/**` the same way the live one does).

The mechanism core never imports the registry. `composeView` and revision capture take an injected `PathPolicy`; composition sites pass `tauPathPolicy` from `@taucad/filesystem/path-registry`. Generated ignore content takes the matching registry rows explicitly, so a non-default policy must pass its own rows.

#### Who owns what inside L1

`WorkspaceFileService` keeps its name, constructor and queue ownership and is a **composition root**: the authority-global surface it serves is topology (mounts, project routes, the project-directory lifecycle, external-change polling, storage-root teardown) plus the per-path primitives that trusted composition still calls. Everything with a shape of its own lives in its own module of `libs/filesystem`:

| Owner                                         | Concern                                                                                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `MutationPipeline`                            | every write: locks, provider commit, cache/index bookkeeping, event emission, batch semantics, the move/copy/duplicate porcelain        |
| `RootedViews` / `createRootedFileSystem`      | one exact mount captured per view; mount-confined, mask-checked reads, writes and porcelain; `ESTALE` after its mount goes              |
| `TreeIndex` / `TreeIndexes`                   | one in-memory metadata index per root, fed by mutations and external facts; serves rooted `search` and `statTree` with no provider walk |
| `content-ops` (`walk`, `contents`, `archive`) | pure read content operations over the port, exported at `@taucad/filesystem/content-ops`; the only place ZIP encoding lives             |
| `project-routes`                              | the only speller of `/projects/<id>`, `/checkouts/<id>`, `/previews/<id>` and `/node_modules`; `MountEntry.kind` carries the route id   |
| `ProjectDirectories`                          | discovery, pending commit, adopt, permanent delete and manifest I/O — the only L1 module that names `ProjectManifest`                   |
| `ExternalChangeIngest` / `RemoteChanges`      | normalised facts from each backend's declared `observe()` capability, and cross-tab remote facts; no `backend === '…'` branch remains   |
| `backend/scope.ts`                            | the storage-scope discriminant (`isDurableScope`, `projectLocatorFor`) the layer above used to infer from a backend name                |

The consumer surface is the **composed view**, not the authority. Protocol version 2 has two wires. `workspaceBridgeService(service)` decides the unrooted wire: nine topology, project-lifecycle, polling and teardown calls plus the scope-required `readScopedFile`, `readScopedShallowDirectory` and `getScopedZippedDirectory`; it serves no per-path content call. Every per-path call uses a rooted connection that declares `root` and `consumer` (`'user'`, `'agent'` or `'working-copy'`). `'user'` and `'agent'` are masked by `composeView`; `'working-copy'` is the raw rooted filesystem for trusted composition only. A missing or unrecognised consumer fails closed before `handlerForRoot`. The fs-client connection owner memoizes one connection per `(root, consumer)` and disposes them together.

`'agent'` means the agent's tools **and any executor of the code the agent writes**: the kernel runtime, GeoSpec runner, Quick Look runtime, host-daemon runtime child and desktop `runtimeFileSystem` route all open that view. Its mask applies to reads, mutations and watches. A recursive remove or move refuses hidden paths at the view root for every consumer and at any depth for an agent; a user may remove a vendored directory containing its own nested store. The Node provider refuses a visible symlink that resolves onto a hidden real path with `ELOOP`, and directory listing drops it. This is defence in depth, not a sandbox: Node, desktop and `tau serve` import bundled project code as a real Node module with `node:fs`, and a browser worker can reach browser storage APIs directly.

Every **bridge** rooted open names a consumer. The language plane is currently a direct internal exception rather than a bridge open: `languageFsSyncAttach` holds a read-only raw `createRootedFileSystem` handle so Monaco sees the checkout rather than the composed overlays.

### L2 — Revisions

- **One repository per project.** It lives in the project's revision control plane at `.git/**` on every host — browser storage included, since the git-storage substrate charter's D29 moved the browser store off `.tau/revisions` so one spelling means one thing everywhere. It is `control-plane` class: hidden from agents, never in a composed view, never exported.
- **`RevisionPort` is the only interface.** The browser and native Git adapters implement it. Ports are widened, never bypassed (N24). Hosts record; agents edit files and never call the port (N26).
- **Identity.** A revision's id is its commit id. A branch is a ref. A candidate line has a change id so it survives rewrites. `Rev N` is a first-parent ordinal on the _selected branch_, computed at display time, never stored.
- **What enters a revision** is exactly the set of paths for which `classify(path).versioned` is true. Nothing else, on any host.
- **Refs beyond branches.** `refs/tau/evidence/*` (compute evidence, N27) and `refs/tau/chats/<chatId>` (chat history shipped with the graph, N28) are the transport of records; the checkout projection is `chat.json` plus foreign `events/<deviceId>.jsonl` segments, while the root `events.jsonl` remains this device's live append log.

The revision effect composition is split by concern:

| Module                   | Owner                                                           |
| ------------------------ | --------------------------------------------------------------- |
| `git-tree-id.ts`         | Git tree object identity over a captured tree                   |
| `handle-table.ts`        | Checkout and capture handle lifetimes                           |
| `case-collisions.ts`     | Portable case-collision discovery                               |
| `apply-tree.ts`          | Tree application, recovery and materialization                  |
| `chat-effects.ts`        | Chat ref recording, publication and replay                      |
| `sync-queue.ts`          | Durable pending-sync queue reads and writes                     |
| `revision-projection.ts` | Versioned change filtering and stable status projection         |
| `remotes.ts`             | `TauCloudAuth`, `publishOverHttp` and `registerProjectOverHttp` |

Each checkout owns a capture memo keyed by `(path, size, mtimeMs)`. It never reuses a stat observed inside the 2 s racy-timestamp window, retains at most 64 MiB by default, and is dropped with the checkout. `applyTree` stages all changed file bytes in one `writeFiles` batch when the surface supports it, then runs the ordered rename, verification and swap stages sequentially.

`RevisionActorsOptions.policy` injects the classifier used by capture, stat admission, temporary-sibling sweeping, evidence filtering and materialization checks. A non-default policy also supplies its own registry rows to `generatedIgnoreContent`; the default `tauRevisionPolicy` pairs Tau's policy and rows.

#### Backends

A backend is a `RevisionPort` implementation that owns the local object store and refs of one project. Three exist; each host picks one per project at open time from the project's control plane, never per call:

| Backend                                      | Store                                                                                          | Hosts                            | Status                                                                                                                                                                                                                                                |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser: `isomorphic-git` over the authority | a standard `.git` layout in the project's storage root, through an `fs` shim over the provider | browser (Home, OPFS, WebAccess)  | **wired** (W3a, 2026-09-12): `createIsomorphicGitRevisionPort`; the hand-rolled store is deleted; stock `git fsck --strict` reads the store with Tau's headers (OQ-W21 ruled). The directory became `.git` in the git-storage substrate charter (D29) |
| Native git                                   | `.git/`                                                                                        | desktop, `tau serve`, CLI, cloud | adapter implemented (worktrees, `update-ref` transactions, 655-line integration suite), reachable only through a dead wrapper; wrapped as a `RevisionPort` in this program                                                                            |
| Future jj over Git                           | `.jj/` with a colocated `.git/`                                                                | a later disk-host wave           | no current adapter; the retired design is retained in research and may be re-created only after its blockers close (EQ14)                                                                                                                             |

Plug-and-play means: the port is the seam, backends are chosen by configuration, and no consumer above L2 names one. A cloud object store is **not** a backend: local working state needs local objects. The cloud enters as a Git remote. `isomorphic-git` supplies browser objects, packs, smart HTTP, log, diff, merge, and tags; Tau keeps revision identity in its `Tau-Metadata` trailer and change-id derivation. The retired jj adapter and wasm algebra are not part of the current runtime; the preserved research is the only starting point for any future jj wave.

#### Remotes

A remote is a peer revision graph reached over **the git protocol and nothing else**. The operator's ruling (EQ4, 2026-09-12): Tau does not invent a transport; the Tau API _is_ a git server, and every other remote is a git URL.

- **One wire.** Git smart HTTP (`info/refs?service=git-upload-pack`, `git-upload-pack`, `git-receive-pack`) plus the **git LFS batch API** for large objects. Disk hosts use native Git (`git fetch`/`git push`) with **zero Tau transport code**. The browser uses `isomorphic-git`'s smart-HTTP client, which already negotiates packs and has no LFS; Tau's browser LFS client keeps `.gitattributes` matching and pointer clean/smudge inside `RevisionPort`, never in the composed view. GitHub, GitLab, Gitea, a bare repository on a shared drive, and the Tau Hosted Remote are all the same kind of remote to a client.
- **The Tau Hosted Remote is a Git server in the Tau API, over object storage.** It runs on Fly, where the API already runs as a container, but no Fly volume holds durable state. A repository's durable form is immutable packfiles plus one small manifest under `tenants/<ownerId>/repos/<projectId>/` in the private R2 bucket (charter D1, D2, D24). Each request hydrates a disposable working copy — a **lease** — from that state and runs stock `git upload-pack --stateless-rpc` / `git receive-pack --stateless-rpc` over it behind Better Auth (bearer token or the browser session). Refs move by Git's own atomic update inside the lease (`receive-pack` is all-or-nothing across refs), and the push is acknowledged only after the manifest is replaced by a conditional write; the HTTP response is withheld until then, and a lost race answers `503` for the client to retry (D4). Any number of stateless workers may serve one repository, with no shared disk and no cross-process lock. Exactly one hook, `pre-receive`, enforces the ref allow-list, fast-forward for every ref family, entitlement, the owner's quota and the per-repository byte ceiling; `update-server-info`, `post-receive` and the dumb-HTTP read layout are gone (D12). LFS objects live under `tenants/<ownerId>/lfs/<projectId>/` behind the batch endpoint. There is no bundle job, no nightly snapshot and no server-side `git gc`: compaction is a writer-side step inside the same manifest write, a manifest names its live and retired packs, and a retired pack stays readable for 30 days, which is what protects a revision named only inside record JSON. The deletion path is a tombstone plus one gated purge (D10, D31).
- **Ref allow-list on the server**: `refs/heads/*`, `refs/tags/*`, `refs/tau/{chats,evidence,artifacts}/*`. Host-local refs (`refs/remotes/*`, `refs/heads/sync/*`, `refs/tau/{owners,workspaces,revisions,transactions,retention}/*`, and `refs/tau/head`) are rejected by the hook and never leave a host (N28).
- **Chats sync as refs** (`refs/tau/chats/<chatId>`, N28): connecting a Tau or Git remote is the chat sync carrier; there is no chat-specific sync plane. Clients read chats from the checkout's `.tau/chats/**` projection on every host (files-first ruling 4). Chat content leaves a device only through a remote the user connected; the Sync consent copy says chats are included, with a per-project _Sync chats_ toggle for projects that should stay files-only (files-first ruling 5, inverted from opt-in to opt-out at the moment of connecting a remote).
- **A project has one owner and any number of collaborators.** `project_collaborator` carries `(project_id, user_id, role)` with `read` or `write`, and `project_invitation` carries `(project_id, email, role, token_hash, expires_at, accepted_at, revoked_at)` on the publication-access pattern. One `ProjectAccessService.authorize(projectId, userId, need)` answers every git request and every project route; a non-member gets 404, a member below the need gets a role refusal. Bytes land in the owner's storage and count against the owner's plan whoever pushed them; the manifest's `committedBy` is the authenticated pusher while the commit author stays the person the client recorded. Registering, publishing and managing collaborators are the owner's alone. Revocation takes effect within the authorization cache window: 5 s per API process, and because any number of stateless workers may serve one repository, a revoked collaborator is refused by the first request after that window on each worker.
- **Remote choice, one at a time.** The Sync region offers _No remote_, _Tau Cloud_, or _Git remote_ (a URL, with GitHub sign-in as the credential when the URL is on GitHub, since GitHub is already a Tau identity provider). The data model is git's own remotes list, so several remotes are representable and a later program can expose them; the pane shows one.
- **Browser → Git remote** goes through the Tau API's CORS proxy for git smart HTTP (the standard `isomorphic-git` deployment pattern, a few dozen lines of forwarding), never a Tau-specific relay protocol. Credentials for third-party remotes are host-resolved: the GitHub OAuth token from the Tau session in the browser, the keychain on desktop, a credential helper on the CLI. No secret is written under a project or workspace directory.
- **A sync conflict** (remote ref moved) is handled by fetch into `refs/remotes/<remote>/*` followed by the ordinary branch merge; a conflict lands on a host-local `sync/<remote>/<branch>` and shows on the Sync row as _Needs resolution_ (see Conflicts). There is no server-side merge.
- **Other blob-like stores are not remotes.** S3, Dropbox, and IPFS have no git transport; exposing them as client-side remote kinds would mean re-implementing a git server per store. They enter, if ever, as (a) server-side storage for a user's Tau-hosted repositories (bring-your-own bucket for LFS objects), or (b) a bare repository on a folder a desktop sync client already mirrors (`git push` to `~/Dropbox/designs.git` works today on disk hosts with no Tau code), or (c) the tenant prefix itself, which is stock packfiles plus a manifest that a user could recover with stock git and no Tau. None is in the first program; the design does not preclude any.

```text
Tau Hosted Remote (apps/api, Fly)
  GET  /v1/git/<projectId>.git/info/refs?service=git-upload-pack|git-receive-pack   (auth: session | bearer)
  POST /v1/git/<projectId>.git/git-upload-pack                                        → git upload-pack --stateless-rpc
  POST /v1/git/<projectId>.git/git-receive-pack                                        → git receive-pack --stateless-rpc
       pre-receive: allow-list · fast-forward · entitlement · quota · per-repository ceiling
                    (the only hook; never parses chat bytes)
       commit:      new packs uploaded under unique keys, then the manifest replaced by a
                    conditional write; the response is withheld until it succeeds
       derived:     accounting, LFS reachability and publication materialization, repaired
                    by the next request that sees a generation mismatch
  POST /v1/git/<projectId>.git/info/lfs/objects/batch                                  → presigned R2 upload/download
  POST /v1/git/proxy?url=<https git remote>                                            CORS proxy for browser clients
```

#### Named versions and publications

- A **named version** is an annotated tag: `refs/tags/<name>` → revision, with `{ note, actor, createdAt }`. Users create one from History (_Name this revision_) or _Where you are_ (_Name…_); hosts create one at every publish. Names are unique per project, renameable, deletable; the revision they point at is immutable.
- A **publication** is a Tau Cloud record `{ projectId, tag, revisionId, visibility, sharedEmails }`. Publishing = ensure the graph up to that revision (and its large objects) is pushed to the Tau Hosted Remote, create the tag if absent, then create or re-point the publication. The API then **materializes the tagged tree server-side** from the pushed pack into the publications service's existing sha256-keyed blob store, so the shipped viewer paths stay exactly as they are: public viewers keep direct CDN URLs (the public cost model depends on them), private viewers keep the grant-rechecking proxy, visibility flips keep moving bytes between tiers. Nothing is uploaded twice; the graph is the source and the blob store is a derived, server-owned projection of one revision. Republishing points the same URL at a new tag; the tag history _is_ the publication history. At cutover the multipart upload path and its upload-era publication rows are deleted; owners re-publish from a revision (A31), with no migration or compatibility path. `tau publish <tag>` is the CLI verb and the dogfood path for `tau-examples`.

#### Checkpoint policy (when edits become revisions)

Prior art converges: Onshape and Google Docs save continuously and mark versions explicitly; Figma and VS Code local history checkpoint on a quiet window and collapse the automatic ones. Tau adopts the same split. Files are always saved to the checkout as they change (files-first); the question is only when a revision is minted.

| Trigger                      | When                                                                                                                            | Gate                                          | Display                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------- |
| `save`                       | `Mod+S` anywhere in the workbench (editor buffers flush first), palette _Save revision_                                         | tree differs from head                        | normal row                                                                      |
| `idle`                       | 5 minutes after the last write with no further writes (OQ-W12; the checkpoint window, distinct from EQ15's liveness idle-close) | tree differs from head                        | collapsed: consecutive idle rows fold into one `n autosaves` row until expanded |
| `hidden`                     | the tab becomes hidden (`visibilitychange`) after a write — the real close in the browser (A39); W6                             | tree differs from head                        | folded with idle rows                                                           |
| `turn`                       | a turn finalizes                                                                                                                | always (a turn with no changes mints nothing) | normal row, chat card                                                           |
| `merge`, `restore`, `switch` | before and after the operation as the operation requires                                                                        | tree differs from head                        | normal row                                                                      |
| `close`                      | the tab is being unloaded (`pagehide`) or the desktop app is quitting, after a write                                            | tree differs from head                        | folded with idle rows                                                           |
| `import`                     | project import — `source: import` on the row; not a `checkout.machine` cut trigger until project import lands on the port       | always                                        | normal row                                                                      |

The gate is one comparison: the cut's `treeId` against the head's `treeId`, both content hashes, so "only when something changed" is exact and cheap. It is only as good as the registry: `thumbnail.webp` (rewritten on every render) is evidence, and `.tau/types/**`, `.tau/tsconfig.generated.json`, `.tau/lockfile.json` are generated, so none of them is versioned and none can trip the gate. Two tabs passing the gate at once mint two candidates; the second CAS fails and that tab drops its revision and re-reads (the existing live-tree Web Lock fences the cut). Idle revisions are immutable like every other revision (no amend, no rewrite); the graph stays append-only and dedupes by content, and display does the folding. A `save` with nothing changed shows _Nothing changed since Rev N_ and mints nothing. On a shared checkout the idle timer is per checkout, not per client.

#### Continuous sync and the close flush

The expectation: finish work in a browser tab, close it, sign in to the desktop app on another machine, and continue from exactly where the tab left off, chats included. A browser gives no guarantee of work after a tab closes, so the design never depends on the close moment carrying more than the last few seconds of work.

- **Push on every revision.** While a remote is connected, every minted revision (any trigger) schedules a push within a short debounce (2 s), coalescing bursts. The push set is two sets, not one (review 3 F4): the **history set** (`refs/heads/*`, `refs/tags/*`) pushes atomically on native git (`--atomic --force-with-lease`) and ref-by-ref in the browser with `main` last and the whole set retried as a unit; the **record set** (`refs/tau/{chats,evidence,artifacts}/*`) pushes per ref, and a rejected record ref never blocks the history set — it lands in the durable queue and shows as a chat-specific state. LFS objects upload before the ref push that references them, so a pointer never lands ahead of its object. There is no separate "sync now" state to remember; _Sync now_ only forces the debounce to zero. The Sync row reads `Backed up` or `Backing up… n revisions` or `Not backed up · n revisions` at all times.
- **Close flush.** A normal project close first asks when runs are active, then cancels them and waits for their persistence to settle, flushes editor/project/chat producers, quiesces revisions and sync, releases leases and the project agent-host hold, and only then stops project resources. A local persistence or release failure leaves the resources live and reports a recoverable visible failure; remote unavailability is safe only after the exact pending work is durably queued. `visibilitychange: hidden` starts the browser flush while promises still run. `pagehide` may resend only a **precomputed, already-serialized single POST** under `fetch(..., { keepalive: true })` — at most 64 KiB, never chats or LFS. Desktop `before-quit` awaits the same session close sequence and offers an explicit bounded _Quit anyway_ escape.
- **Durable queue.** A push not acknowledged by the server stays recorded in the checkout's control plane (`.git/sync-pending`) and is retried on the next open of the project on that device, before anything else. The state is visible, never silent: the Sync row and the header chip show `Not backed up` until the acknowledgement arrives.
- **Open pulls first, under a bound.** Opening a project that has a remote fetches before the first render of the tree. `sync.machine` owns the offline exit, the 3 s local-render window, and the 10 s abort; its request signal cancels HTTP/native work and release drains any mutation already admitted. All fetched user branches become selectable without allocating linked checkouts; only the active branch is integrated, and another branch materializes on explicit _Switch_ or _Work in_. A clean, unleased live checkout may fast-forward. Dirty, newly changed, leased, or lost-CAS state is preserved and deferred or surfaced as conflict. Incoming trees are fully preflighted and apply under the checkout fence with rollback on partial failure. Chats appear because `refs/tau/chats/*` came with the fetch and only the fetch path projects validated `chat.json` and foreign `events/<deviceId>.jsonl` entries; the root `events.jsonl` remains local.
- **What "where I left off" means in this program**: the same files, the same revision history, the same branches and named versions, the same chats with their cards. Which chat, files, and pane were open is client UI state and is not synced; a later program may store it as a record.

#### Conflicts

- Conflicts arise in exactly two places: merging a branch into another, and syncing when the remote's ref moved. Both funnel into the same three-way merge. A sync conflict is recorded on a host-local branch `sync/<remote>/<branch>` and shown on the Sync row as _Needs resolution_; a conflicted revision is never pushed (I-CONF).
- A conflicted merge mints a **conflicted revision on the source branch** (jj-style: conflicts are recorded, never left as loose files) and never touches `main` or the live checkout. The pane shows _Needs resolution_ on that branch with per-file rows: _Keep mine_, _Keep theirs_, _Open in editor_ (text files, conflict markers), _Ask chat to resolve_ (starts a turn attached to that branch's checkout with the conflict record as context). Binary and parametric files (STEP, meshes, `.tau/parameters/**`) offer choose-one only.
- Resolution mints a normal revision on the branch; the user then merges or syncs again. Nothing is auto-resolved.

#### Large-object policy

- Large objects go through **git LFS**, the standard every git client and host already understands, instead of a Tau-specific path. Tracking rules are generated into `.gitattributes` from the path registry (derived, like the ignore file): binary types always, and any file at or above 1 MiB (the jj `snapshot.max-new-file-size` default) by a size filter. Trees then reference LFS pointers; the bytes live in the LFS store of whichever remote the project syncs to (R2 for Tau Cloud, GitHub's LFS for a GitHub remote, with its quota).
- **What the user sees** (EQ7): nothing about LFS. Identity, restore, compare, and history are unchanged. The Sync region shows storage against the plan (`2.1 GB of 10 GB`) and a push over quota is refused with the list of files that would exceed it. Large authored inputs always sync. Generated evidence is default-off and controlled only by `tau.json.syncLargeExports`; when true, `exports/**`, `thumbnail.webp`, `.tau/artifacts/**`, `.tau/tool-results/**`, and `.tau/offloaded-tool-results/**` are captured under the exact record ref `refs/tau/evidence/exports` and use LFS as needed. Fresh devices restore only absent evidence paths, never overwrite local evidence. Turning the option off stops future transfer without deleting local or remote bytes.
- Text and parametric sources stay far below the threshold; imported STEP and meshes are the expected LFS objects. A GitHub remote's LFS limits are surfaced on the remote row before the first push rather than discovered as a rejection.

#### Attribution

- Every revision carries an **actor**. For a signed-in user: `{ kind: 'user', id, email, name }` from the session. For an agent: `{ kind: 'agent', id: <model>, runId, onBehalfOf: <user actor> }`. For a user who chose anonymity or is not signed in: `{ kind: 'user', id: 'anon:<stable per-workspace hash>', anonymous: true }` with no email.
- Mapping to native git: author = the user actor (`Name <email>` or `Anonymous <anon-hash@users.noreply.tau.new>`), committer = `Tau <noreply@tau.new>`, trailers `Tau-Actor: agent <model> run <runId>` and `Tau-Trigger: <trigger>`. Stock git shows sensible authorship; Tau reads the trailers.
- Anonymity is a workspace-level setting and a per-publication choice; switching it never rewrites history.

#### Diffs

_Compare_ opens the existing text diff viewer (the Shiki-based `DiffViewer` used by chat file cards) for revision-vs-revision and revision-vs-checkout, per file, on three surfaces: History hover, the chat card's file rows, and conflict rows. Geometry diff in the viewer is a later, separate capability with the same inputs.

#### Undo

Undo is within a checkout's unsaved state; revisions are across it. The editor's undo stack never crosses a revision boundary, and _Restore_ offers its own one-level _Undo_ toast.

### L3 — Checkouts

A checkout is Git's worktree, made addressable. It answers the question _where does work happen_, separately from _which line of history is it on_ (branch) and _who is doing it_ (lease).

- **The live checkout is the project directory** (git's main worktree). It tracks `main` by default.
- **Linked checkouts** are additional working copies, one per branch, materialized in the host-private area. They are _outside_ the project directory, so nothing about them needs excluding from capture, export, watches, or the agent mask by path spelling — physical separation supplies the exclusion. Native backends use `git worktree add`; the browser backend implements the same registry with directories. The private area is per host: on browser storage roots it is `<storageRoot>/.tau/checkouts/<projectId>/<checkoutId>/`, reached through a **checkout route** `/checkouts/<checkoutId>` installed from persistent project-root configuration (authority Rule 3, same storage root, class `authored`, invisible to discovery) so `createRootedFileSystem('/checkouts/<id>')` needs no new capability; on disk hosts it is the host data directory, never any served directory, because on `tau serve` the served directory _is_ the project and native Git refuses a worktree inside its own worktree.
- **One checkout per branch.** This is Git's rule and it keeps the UI honest: a branch row _is_ its checkout, and "who is working on `fillet-exploration`" is the set of leases on that branch's checkout.
- **Chats attach to a checkout by id, not by mode.** A chat record carries `checkoutId`. Every new chat attaches to the live checkout by default, including when another chat holds a lease. Only an explicit user _New branch_ or _Work in_ choice creates or selects another branch. Subagents spawned by a chat inherit its checkout; peer chats deliberately collaborating on one task attach to the same checkout. Concurrency inside one checkout is one tree, last write wins per file, and one revision per turn capturing the whole tree with every active lease named in its provenance.
- **The workbench attaches too.** The workbench's checkout selection is just another attachment; "Current" in the Revisions pane marks the branch whose checkout the workbench reads.
- **Switch and Restore respect leases and the one-checkout-per-branch rule.** If a lease holds the live checkout, Switch never re-bases it: it creates (or reuses) the branch's linked checkout and re-roots the workbench there. Restore applies a revision to the _selected_ checkout and lets it track the revision's branch only when no other checkout tracks it; otherwise the checkout is `detached`. The registry enforces this at `addCheckout` and at `setHead`.
- **The checkout registry lives in the control plane** (`.git/checkouts/<id>.json` on the browser backend; `.git/worktrees/` in the project's own repository natively, whose linked trees are created under the host data directory at `<config dir>/checkouts/<projectId>/<id>`) and is reached only through `RevisionPort.listCheckouts / addCheckout / removeCheckout`.
- **A checkout never becomes a revision.** Finalizing a turn on a checkout _mints_ a revision from the checkout's versioned paths and advances the checkout's branch by compare-and-swap. A linked checkout persists while its branch has work; after merge it is disposable and "Discard" removes both.
- **Durable state of a project = revision graph + refs + live checkout.** Linked checkouts, leases, composed views, tree caches, `Rev N` numbers, dirty flags, and provenance labels are all regenerable from those three, and linked checkouts with unfinalized edits are the one thing whose loss loses work, which is why a turn always finalizes or discards.

### L4 — Composed view

```ts
composeView(checkout: Checkout, opts: { consumer: 'agent' | 'user' }): ComposedView
// ComposedView = RootedFileSystem + { provenance(path): Provenance }
// Provenance = { source, versioned, agentAccess, identity?, overrides? }  — agentAccess is the agent's access (P10); user gating reads source/versioned
```

- **Same function, all hosts, both consumers.** Browser worker, `tau serve`, the Electron utility, and the CLI call the same `composeView`. The agent's tool filesystem and the Files pane are two callers of one function over the same checkout; they cannot disagree.
- **Overlays** are read-only and are never stored in the project: system skill bundles at `.agents/skills/<slug>` (identity `skill:<slug>@<version>#<fingerprint>`), dependencies at `node_modules` (derived; regenerated per host, N18). A project-authored path under an overlay's root _overrides_ the overlay as a whole bundle (never a per-file merge); the composed entry then reports `source: 'project'` with `overrides: <overlay identity>`.
- **The mask differs by consumer, the tree does not.** For the agent, `records` paths are read-only and `control-plane` paths are hidden. For the user, records are visible, dimmed, and editable only through host UI. The set of paths is the same.
- **Provenance is data, labels are catalog.** The view returns `{ source, versioned, agentAccess }` (`agentAccess` is the agent's access; user-facing refusal is `source !== 'project'`, dimming is `versioned === false` — ruling P10, W2 review R2); the UI maps that tuple to copy through one catalog. No presentation string crosses the wire.
- **Events ride the view.** A composed view owns a rooted event port. Writes through the agent's view reach the UI's view of the same checkout through the authority's rooted watch plane, on every host. There is no path on which an agent write is invisible to a UI reading the same checkout.

### L5 — Porcelain

One workbench (one project route, one lane set) has **one checkout selection**. All of Files, editor tabs, viewer, parameters, main-file selector, and the Revisions pane read that selection through `composeView(selected)`. Selecting is one verb, **Switch**, with two implementations the user never distinguishes: if the target branch has no linked checkout, the live checkout applies it (git switch, DT1 as shipped); if it does, the workbench re-roots every consumer at that checkout (`cd` to the worktree). Because every consumer already takes a rooted view, re-rooting is re-issuing views, not new plumbing. The chat's composer chooses which checkout the _next turn_ works in; the workbench follows the chat's checkout by default and can be pinned elsewhere.

## How the app drives each layer

### A turn, end to end

```text
prepare(chat)
  ├─ checkout = chat.checkoutId ?? live checkout
  │     (a subagent inherits its parent's checkout; only the user may create or pick another branch)
  ├─ if the checkout is dirty vs its head → mint base revision (source 'user') first
  └─ write lease .tau/runs/<runId>.json { checkoutId, chatId, baseRevisionId }

run
  └─ agent reads/writes composeView(checkout, 'agent'); every other attachment to the checkout (workbench, peer agents)
     sees each write via the rooted watch plane

finalize
  ├─ capture = versioned paths of the checkout (registry-driven)
  ├─ revision = writeRevision({ parents: [base], tree: capture, provenance: { source: 'agent', runIds: leases on this checkout } })
  ├─ CAS checkout.branch ← revision           (main for the live checkout; the linked checkout's branch otherwise)
  ├─ emit turn.finalized (host-attested) → chat card "Rev N"
  └─ retire lease

merge (user verb "Merge into main")
  ├─ three-way merge(head(main), head(branch), mergeBase) → apply to main's checkout
  ├─ conflict → both branches kept, conflict record surfaced, checkout untouched
  └─ success → merge revision { parents: [main, branch], source: 'merge' }; CAS main; the linked checkout is disposable

switch (user verb "Switch")
  ├─ branch has a linked checkout → workbench re-roots at it
  └─ otherwise → apply head(branch) to the live checkout; live tracks branch

restore (user verbs "Restore", "Return to latest")
  └─ apply revision R to the selected checkout; it tracks R's branch, or 'detached' when none names R

sync (user verb "Sync", default remote)
  ├─ fetch(remote) → expose all user branches; integrate only the active clean, unleased branch
  └─ push(remote, tracked refs + refs/tau/*, expected) → 409 → fetch and retry once, then surface
```

These compose as **one actor tree per project**: a root `project-revisions.machine` is the single actor a host creates. The six always-on children (`checkouts`, `sync`, `remote`, `branch`, `restore`, `publish`) are **invoked** for the root's whole life, so they stop with it; the variable-count children (`checkout` per registered checkout, `turn` per admitted turn) are spawned with a stored `ActorRefFrom` in context and stopped with `stopChild` on removal and on root `exit`. Children get `parentRef` through `input` and address siblings by sending to the parent, which routes (the `project.machine` precedent); **`systemId` is not used**, because the app is one XState system and a second live project would collide. The root also owns the **workbench selection**: `selectedCheckoutId` and `follow: 'chat' | 'pinned'` in context with `switch { branch }`, `followChat`, `pinTo { checkoutId }` events and the D10 apply-to-live-versus-re-root guard, which needs `checkouts`' lease set. `turn.finalized` has three consumers of two kinds: a **send** to the parent (routed to `checkouts`, the checkout, and the chat's session) and an **emit** for the chat card. Where the tree runs is decided, not open: `project-revisions` and its children run **in the file-manager worker** beside the authority, the object store, and the hashing (so tree-hash gates never cross the bridge), and the worker publishes one coalesced `RevisionStatus` projection per project (`{ projectId, checkoutId, branch, dirty, minting, headRevisionId, follow, attention, restore, remote } — no ordinal on the wire, `Rev N` is derived at read from the first-parent walk (I3; W5 review R12)`) that React reads through a stable selector; the UI worker of the agent host and the Electron utility get the same machines with their own actors. `sessions`, `project-session`, and `chat-session` run on the main thread, since they own main-thread resources.

Rules:

- **Machines import no filesystem, git, React, or DOM.** Effects (`cut`, `push`, `fetch`, `computePlan`, `applyPlan`, `writeRecord`, `persistQueue`, `sweepLeases`) are named actors the host supplies through `machine.provide({ actors })`, the pattern `RevisionProvider` already uses for `computePlan`/`applyPlan`. One-shot effects are promise actors (`fromSafeAsync` in the app, `fromPromise` with `signal` in packages); **the lease is a `fromCallback` actor**, because the Web Lock is held for the callback's lifetime across the event-driven `leased` state and is not reentrant; one lease actor per checkout is the lock's only owner. No function lives in context (no `persist` callback): every write is an actor whose inputs the test asserts. Every machine has a `failed` state or a non-terminal failure edge for each invoked effect. A machine test uses fake actors and a fake clock, asserts states, sent and emitted events, and actor inputs, and runs in plain Node with no jsdom.
- **Coalesce at the seam, debounce in the machine.** The content-change stream sends one `changed { paths, generation }` per change event, never one per path; a 50-file batch is one transition. Token deltas never enter a machine: `run.lifecycle: running` alone means generating, and tool-part transitions are batched per event by the transport adapter. The sync push debounce and the idle window are policies the machines own. `syncState` carries settled values only, so a backoff tick never re-renders eight project rows.
- **One machine, every host.** The browser (in the UI worker or provider), the Electron main process, `tau serve`, and the CLI instantiate the same machines with their own actors. Host-attested `turn.finalized` (with `turn.conflicted`/`turn.failed`, A4) is the `turn.machine`'s emitted settlement on every host, so the schema is one by construction, not by convention.
- **UI machines stay in the UI.** `file-manager`, `project`, `editor`, and `chat-persistence` machines keep their ownership; the revision machines connect to them by events, not by shared context: the content-change stream feeds `checkout.machine.fsWrite` (the seam `RevisionProvider` already wires), the editor's `flushNow` completes before `close` is sent, `sync.machine.syncState` drives the pane and chip.
- **Close and quit reuse the hooks that exist, with ordering made real.** The browser's `UnloadProvider` / `useFlushOnClose` registry stays the single listener, but its callback becomes `(reason: 'hidden' | 'pagehide') => void | Promise<void>` and it runs in two phases: flush registrants (the editor's existing `ProjectSessionFlushRegistration.flush()`, which awaits `storing: idle`, and the chat actors) settle first, then the session registrants receive `hidden` (→ the idle trigger) or `pagehide` (→ `close`). Insertion order is never relied on. The desktop's `before-quit` shutdown promise awaits `sessions.quit` → `quiesced` under a bound, with _Quit anyway_ sending `quitAnyway` that resolves it early.
- **Ownership has no cycles.** `chat-session` does not own turns: it sends `prepare` and `turnCompleted` to its project session, which forwards to the worker-side `project-revisions` root; the root spawns the `turn.machine`, which asks its `checkout.machine` to `cut`; `turn.finalized` comes back the same way. The `sessions` singleton is created with `createActor` in a store module and provided through context (the `ChatSessionStore` precedent), never with `useActorRef`, so Strict Mode cannot double-start every project. Per-route views use `useActorRef` as today.
- **Records are the durable form, never machine snapshots.** No machine persists its XState snapshot; `.tau/runs/<runId>.json`, the graph, git's own remote config, and `.git/sync-pending` are the truth, and every machine rehydrates from them through `input` at start (I3: derived at read time). A snapshot format would be a second schema to migrate; the records already exist.
- **What is not a machine**: pure functions (`classify`, `composeView`, the revision algebra, hashing, fold rules), the port adapters, the git server, the `Rev N` / dirty / "Current" / `Follow chat` derivations (selectors over the graph and machine snapshots), and `import-github.machine`, which stays as it is; once EQ11 lands its download actors can become a clone through the remote actors with no state change, which the deferred import ruling leaves for later.
- **Placement**: every machine is scaffolded by the workspace machine generator (`create-machine` skill) as one direct package subpath (`@taucad/revisions/turn-machine`, `…/checkout-machine`, …), each exporting exactly one machine value plus its selectors and guards; the package root barrel carries no machine value. `xstate` enters `packages/revisions` as a **peer plus dev dependency**, the `packages/camera` and `packages/three` precedent; the five-machine composition lives at the owner as `createProjectRevisionsActor` in `/revisions/revision-effects` (W3c: `packages/host` names no `xstate` type and holds no `xstate` dependency; `apps/ui` mounts the same composition in the file-manager worker). Fencing: `checkout`'s `fence` serialises mints per checkout **within one process** (browser: the live-tree Web Lock; Node: in-process); across processes the only fence is the port's expected-old ref CAS — `applyTree` writes are unfenced across processes (W3c review R13; a disk host that needs more decides it in W9). Nothing under `libs/filesystem` depends on XState: the authority is an effect, never a consumer of a machine. Events are `camelCase` per the XState policy; the kept restore states are renamed from the current `SCREAMING_SNAKE_CASE` when they move.

Rules that follow:

- **Liveness is orthogonal to navigation.** Opening a project route sends `open` if the project is closed; leaving sends nothing. The user can iterate on several ideas in one project (several chats on `main`, or on branches) and on several projects, and every one keeps running while another is on screen. Returning is instant because nothing was torn down.
- **One session owns everything project-scoped.** The content and tree services, kernel workers, the agent-host attachment, compute admission, watchers, and the revisions actor system are children of the project session and die with it, never with a route. Run settlement and host registration therefore outlive navigation, which closes two defects the trace found. Compute admission becomes per live project instead of single-project.
- **Close is a verb and a policy, never a side effect.** _Close_ on a project asks when runs are in progress, cancels and settles them, flushes all local producers, quiesces revisions/sync, releases leases and the project agent-host hold, then stops children. A failed local step leaves resources live with a visible recoverable failure. Remote failure may close only after its pending state is durably queued. _Close_ on a chat cancels its run, releases its lease, and keeps its record. Policy closes are visible and never admit a running, dirty, minting, or unpushed project.
- **Budget, stated.** The browser holds at most **8** live projects (operator ruling 2026-09-12, OQ-W25); each costs a kernel worker with a 100 MiB geometry buffer and an agent-host worker per run, so the idle window and the visible policy close carry the memory story rather than a low cap; desktop is bounded by memory only. When a ninth open arrives, the registry closes the least recently touched _idle_ project and says so; if none is idle it refuses with the list to close. Idle closes after 30 minutes with the project hidden (OQ-W26); the window is per workspace, never per project.
- **App quit and tab close** send `quit` to the registry, which runs every live session's `closing` with the flush of D28; on desktop the shutdown promise awaits it.
- **Desktop and browser share the semantics.** The desktop always-on launcher per workspace root becomes the `agentHost` child of the project session; a closed project on desktop has no launcher. The same machines, different injected actors.
- **The sidebar is a selector.** Every glyph is derived from `sessions`, `project-session`, `chat-session`, and `project-revisions` snapshots at read time. The only persisted status is `unread`, a per-client record, because it is about what this person has seen on this device.

### The relations, stated plainly

- A **project** has one revision graph, one live checkout, and zero or more remotes.
- A **branch** is a named line in that graph. `main` is what the live checkout tracks by default; only users create other branches.
- A **checkout** is where edits happen: the live one is the project directory, linked ones are private working copies, one per branch. A checkout is never _in_ the graph. Chats, subagents, peers, and the workbench attach to a checkout by id; sharing one is how peers collaborate.
- A **turn** takes a lease on a checkout, edits it, and ends by minting **one revision** onto the checkout's branch.
- **Merging** a branch produces a merge revision on `main` and makes the linked checkout disposable. The branch ref may be deleted then (user verb "Discard") or kept.
- **Restore** does not fork history; it applies an older revision to the selected checkout. The next turn from there mints a revision whose parent is the restored one, which _is_ a fork — and the graph records it as such without any synthetic `history/…` branch.
- **Sync** exchanges refs and objects with a remote and never touches a working tree except through the same merge path a local branch uses.

### What each surface must never do

- Panes must not read different checkouts from each other. (Fixes the "chat works elsewhere" symptom.)
- The Files tree must not show a linked checkout as a directory of the project. (Physical separation makes this automatic.)
- Revision numbers, dirty state, and "Current" must not be derived from the transcript.
- No caller may test a path prefix to decide access, versioning, or visibility. It asks the registry.
- No agent may read or write the revision control plane or the lease records.
