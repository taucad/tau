# Workbench capability tracker

Living inventory of **what Tau exposes through files and programmable controls**,
and the work needed for parity. Last audited **2026-10-01**, against `geospec` at
`faecc9ac8f456b7fa5639fc0eb146012e3e499c8`. The isolated
`spike/filesystem-scene-api-oct2026` experiment is branch work. This is a source
and focused-test audit, not a fresh execution of every UI acceptance suite.

## Reading the status

| Status          | Meaning                                                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Complete**    | Implemented on the audited `geospec` baseline, within the stated limits. Does not imply released to npm or deployed. |
| **Partial**     | A useful subset is implemented; the missing portion is named.                                                        |
| **In progress** | Implementation exists on an active branch or in unmerged work; acceptance/integration remains open.                  |
| **Planned**     | A linked design exists, but the capability is not integrated. A successful spike alone stays planned.                |
| **Absent**      | No Tau adapter/authoring path found. This is a parity gap, not an approved implementation commitment.                |
| **Unverified**  | Upstream/import behavior may exist, but the reviewed evidence does not establish Tau support.                        |

These definitions match the [kernel tracker](../kernels/README.md). Every status
below concerns the named programming route, not whether its UI exists. File
state, explicit authorized commands, device state and transient interaction are
different contracts. A schema alone does not establish a live consumer.

## Filesystem authority review

The [path registry](../../packages/filesystem/src/path-registry.ts) and
[authority policy](../policy/filesystem-authority-policy.md) remain authoritative.
`.tau/workbench/**` is live-root, agent-writable saved presentation state, not a
revision-control store. A host consumes that state through its existing owners.
Do not introduce a generic dispatch mechanism from arbitrary JSON keys to host
commands.

| Classification                                                                  | File programming policy                                                                           | Evidence / boundary                                                          |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Declarative saved presentation                                                  | Strict, bounded, versioned records; invalid bytes preserved; reconcile into existing owners       | [workbench codecs](../../packages/workbench/src/records.ts)                  |
| Authored source, parameters and asset data                                      | Existing rooted filesystem and runtime admission; source execution is a separate authority        | [filesystem policy](../policy/filesystem-policy.md)                          |
| Secrets, credentials, billing, authorization, trusted filesystem roots          | Never project-authored authority; no workbench key may grant them                                 | [filesystem authority](../policy/filesystem-authority-policy.md)             |
| Publishing, sharing, permanent deletion, paid work and physical machine actions | Explicit commands with their existing permission/approval boundaries; never replayed by a watcher | [protected record/control classes](../policy/filesystem-authority-policy.md) |
| Transient hover, focus, gestures, tool mode                                     | Session interactions; no invented persisted semantics                                             | [view exclusions](../../packages/workbench/src/records.schema.ts)            |
| Device capability and pixel sizing                                              | Device owner; portable project cannot force an unsupported backend                                | [graphics backend policy](../policy/graphics-backend-policy.md)              |

## Keeping this document current

1. Update the relevant row and audit date when schema, consumer or acceptance changes.
2. Link implementation and meaningful checks, recording branch and integration state.
3. Use **In progress** for unmerged implementation; do not promote a spike to baseline **Complete**.
4. Separate schema acceptance, semantic geometry validation, rendered-pixel acceptance, release and deployment.
5. Recheck the existing owner queues; this inventory is not a second execution queue.

The focused spike checks and runnable commands live in its [README](../../packages/workbench/src/experiments/filesystem-scene/README.md).
Baseline UI suites, native pixels and production cloud behavior have not been
rerun for this inventory. Future work: renderer-owned consumption, durable
host-store recovery, production rooted-provider wiring, broader format closure,
and the existing pane/configuration program. None is represented as delivered
by this spike.
