# Tau Grafana Alerts

JSON files in this directory are alert **rule groups** consumed by the versioned Terraform bundle for hosted provisioning and by
`apps/api/scripts/sync-grafana-dashboards.sh` for local development. Each file defines
one rule group; each rule inside a group has a stable `uid` so re-runs are
idempotent (the local sync updates groups in place without deleting rules).

## Datasource UID assumptions

Rules reference datasources by `datasourceUid`. The sync script does **not**
remap UIDs — they must already exist on the target Grafana instance.

| `datasourceUid` | Required type | Where it lives                                                                                                                                                                                                                                                                                                        |
| --------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prometheus`    | Prometheus    | Local: `infra/grafana/provisioning/datasources/datasources.yaml`. Prod: provisioned in Grafana Cloud as `prometheus`.                                                                                                                                                                                                 |
| `loki`          | Loki          | Local: same provisioning file. **Prod note:** Grafana Cloud's logs datasource UID is typically `grafanacloud-logs`. Re-create it as `loki` (or update the rule UIDs) before syncing `tau-critical.json`'s `database-startup-failure` rule, otherwise the rule will fail to evaluate with `failed to find datasource`. |
| `__expr__`      | Expression    | Built-in to Grafana, always available.                                                                                                                                                                                                                                                                                |

Storage selectors follow binding contract v2 (`../README.md`): one query per app, each carrying that
app's `service_name` (`tau-api`, `tau-storage`, `tau-mirror`); Fly `fly_*` series carry only the `app`
matcher. The accounting scheduler's gauges are computed once and shared, so every API Machine exports the
same figure and they are read with `max`, never `sum`. The hot-project ranks are per Machine (each ranks
the commits it served), so `max(A or B)` across Machines and apps is a lower bound on the busiest project. Not shipped, because nothing emits their series yet (W14 drafts
kept for the package that adds them): `storage-migration-integrity` and migration aborts (OB5's migrator),
worker slot use and disk headroom against the D20 reserve (no `tau_git_capacity_slots`,
`tau_git_disk_reserve_bytes`), R2 429s per minute (no `tau_storage_attempts_total`), compute lookups and
the compute triggers (OB7), the stage-3 serializer trigger (OB8), `trigger-c3-git-cpu-cost` (slot use),
`storage-b2-erasure-overdue` (no erasure gauges), `storage-derived-lag` (OB4).

Webhook **settlement lag** (top-up created → settled) has no first-party metric;
monitor it via Stripe Dashboard → Developers → Webhooks (delivery latency +
failure rate on the Tau endpoint) — part of the launch-checklist click-ops.

## Adding a new alert

1. Append a new object to the `rules` array of the appropriate file.
2. Pick a stable, kebab-case `uid`; provisioning retains it for in-place updates.
3. Use `severity: critical` for P0, `severity: warning` for P1, or `severity: info` for a trigger
   (email only; it also needs `kind: trigger`, `trigger` and `package`). Set `annotations.runbook_url`
   to a `docs/handbooks/cloud/**.md` page, and keep the `uid` unique within its first 20 characters
   (see `../README.md`, binding contract version 2).
4. Update the local YAML copy and run `pnpm nx run scripts:validate-grafana`.
5. Sync locally; promote the pinned definition commit in Tau Cloud for hosted changes.

## Adding a new Loki LogQL alert

Loki rules need three `data` entries: a `range` Loki query, a `reduce`
expression (`__expr__`), and a `threshold` expression (`__expr__`). The
`condition` field at the rule top-level must reference the threshold's
`refId`. See `database-startup-failure` in `tau-critical.json` for the
canonical shape.
